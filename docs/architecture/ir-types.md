# IR Type System Reference

Source: `src/ir/types.ts`, `src/ir/sdk-behavior.ts`

The intermediate representation (IR) is the contract between the parser and all language emitters. It uses plain TypeScript interfaces (no classes) with a discriminated union type system.

## Top-Level: ApiSpec

```typescript
interface ServerVariable {
  default: string; // Fills the placeholder when nothing else is chosen; OpenAPI requires it
  enum?: string[]; // The values the variable may take; present only when declared (and non-empty)
  description?: string;
}

interface ServerEntry {
  url: string; // As written, placeholders included: https://{region}.api.example.com
  description?: string;
  variables?: Record<string, ServerVariable>; // Keyed by placeholder name; present only when declared
}

interface ApiSpec {
  name: string; // From info.title
  version: string; // From info.version
  description?: string; // From info.description
  externalDocs?: ExternalDocs; // The document's top-level externalDocs, when usable
  baseUrl: string; // servers[0].url with each variable's default filled in
  servers?: ServerEntry[]; // The document's servers; every operation inherits them unless it carries its own
  services: Service[]; // Grouped operations
  webhooks?: Webhook[]; // Top-level `webhooks` map (OpenAPI 3.1); absent when the document has none
  models: Model[]; // Schema objects
  enums: Enum[]; // String enums
  auth?: AuthScheme[]; // Authentication schemes
  security?: SecurityRequirementSet[]; // Document-level default requirements (see Operation.security)
  sdk: SdkBehavior; // Runtime policies (retry, errors, telemetry, etc.)
}
```

The `servers` array contains the document-level server entries from the OpenAPI spec — the ones every operation uses unless it carries `servers` of its own (see "Operation-level servers" below). `baseUrl` is always the first document server's URL, resolved: each `{name}` placeholder is replaced by that variable's `default`, so a client built on `baseUrl` requests `https://eu.api.example.com/v1`, not `https://{region}.api.example.com/v1`.

**Server variables.** `ServerEntry.url` keeps the template as written and `variables` carries what the document declares for it (same shape in OpenAPI 3.0 and 3.1), so an emitter can offer the choice — an environment or region picker — rather than only the default. There is no `resolvedUrl` on `ServerEntry`: `resolveServerUrl(server)` from `src/ir/server-url.ts` (exported from the package) returns `{ url, unresolved }` for any entry, which is exactly how the parser produced `baseUrl`. It is plain string scanning: a variable may appear more than once, the substituted value is not scanned again, and no pattern is built from the variable names.

The parser checks every server, not only the first, and reports each problem once with an `[oagen] Warning:` that names where the list sits (the document, a path item, an operation): a variable without a usable `default` is omitted from `variables` (the IR requires one) and its placeholder stays in the URL; a placeholder that names no declared variable stays in the URL; a `default` outside the variable's `enum` is kept as written. A declared variable the URL never uses is kept without comment. `default` and `enum` entries are strings; a number or boolean (YAML reads `default: 8443` as a number) is carried as its text. `variables`, `enum` and `description` are absent, not `undefined`, when the document does not declare them.

**Operation-level servers.** A Path Item and an Operation can declare `servers` of their own, and OpenAPI gives the operation's precedence over the Path Item's, which takes precedence over the document's. `Operation.servers` carries the winning list — the same `ServerEntry` shape, variables included, normalised by the same code as the document's, so `resolveServerUrl` works on it too — and only when it differs from `ApiSpec.servers`: an operation that declares nothing at either level, or whose winning list restates the document's, has no `servers` key and inherits. "Differs" is structural, by `serverListsEqual` (exported from the package): the two lists must have the same length and, position by position, the same `url`, `description` and `variables` (same names, each with the same `default`, `enum` in the same order, and `description`); a different description alone is a difference. The one exception is OpenAPI's default server: a list that is empty and one that holds nothing but `/` without variables both mean it — `isDefaultServerList` (exported from the package), the entry's description aside — and an operation whose list means it under a document whose list means it too inherits, so one that writes `/` out under a document that declares no servers inherits. A list with any other entry is compared as written, `/` entries included, because position decides the default host. Precedence is applied before the comparison, so an operation that restates the document's servers under a Path Item that diverges inherits. To find where a request goes, take `op.servers ?? spec.servers`; `baseUrl` is always the document's first server, resolved, whatever any operation declares.

Edge cases: `servers: []` at path or operation level is treated as absent — OpenAPI defines an empty list only at the document level (where it means `/`), not as an override — so the operation falls through to the next level; the same goes for a list whose entries are all unusable (not an object, no `url`, or a blank `url`), while the usable entries of a mixed list are kept. A document with no `servers` (or `servers: []`) means OpenAPI's default server, and so does one whose every server is `/` without variables, so an operation that declares any other usable list under either carries it, while one that writes `/` out under either inherits. `baseUrl` stays `''` for a document with no `servers` and is `/` for one that writes the default out; `ApiSpec.servers` is carried as written either way. The parser does not resolve a Path Item written as a `$ref` (its operations are not extracted at all), so there is no Path Item `servers` to carry for one. The operations of one Path Item that inherit its list share the same array.

The differ reports a change as `serversChanged` on an `operation-modified` change, always breaking (the operation's requests go elsewhere). It judges where the operation is actually served from, `op.servers ?? spec.servers` on each side, not whether the field is set: a document that moves to where an operation already pointed (so the operation's override disappears) is not a change to that operation, and an operation that inherits on both sides is never reported here even when the document's own list moved — that is the document-level diff's. The comparison follows the document-level rule rather than `serverListsEqual`: the two effective lists are matched as multisets on `url` template plus variables (names, defaults, enum values as a set), so position, `description` on a server or a variable, and enum order do not count; a reorder counts only when it moves the first entry's resolved URL, the operation's default host. Any other variable difference counts, including one the document-level diff would call additive, since one boolean cannot carry that distinction. OpenAPI's default server is one list here too: an operation served from `/` written out and one served from a document that declares nothing are served from the same place.

`security` is the document-level `security` list, in the same shape as `Operation.security`; every operation that declares no `security` of its own inherits it. It is `undefined` when the document declares none. The differ reports it differing between two documents as one `security-changed` change, with `oldSecurity`/`newSecurity` (`[]` for none); see the security paragraph under [Service & Operation](#service--operation) for how the lists are compared and classified.

`webhooks` is the document's top-level `webhooks` map (OpenAPI 3.1) as a list of `Webhook`, in document order; see [Webhook](#webhook). The key is omitted — not set to an empty list — when the document declares none, so the IR of such a document is unchanged.

### ExternalDocs

```typescript
interface ExternalDocs {
  url: string; // Exactly as written in the document
  description?: string; // Only when it has non-whitespace content
}
```

An OpenAPI External Documentation Object — the document's way of linking to fuller documentation — carried on `ApiSpec` (the top-level `externalDocs`), `Service` (from the document tag, see below), `Operation`, `Webhook` (its operation's own, read as `Operation`'s is), `Model`, `Field`, `Parameter`, `ResponseHeader` and `Enum`, so an emitter can add it to a doc comment (a JSDoc `@see`, say). The key is present only when the document declares an entry with a non-blank `url`: a non-object, a missing or blank `url`, is dropped — silently, the way a malformed document tag is, since the parser ignored `externalDocs` entirely before and a malformed value must keep parsing. `url` is kept verbatim. OpenAPI allows it to be relative to the document's own location, which the parser does not know, so it is neither resolved nor rewritten, and `expandDocUrls` leaves it alone too; `expandDocUrls` does expand relative links inside `description`, which is CommonMark like every other description it walks. `description` is present only when it has non-whitespace content and is kept verbatim otherwise.

A `Model` built from an inline schema — a request body, a response, a `oneOf` variant, an object nested in a component field, array items, an `allOf` merge, a discriminated `allOf` + `oneOf` variant — carries the `externalDocs` of the schema it was built from. A wrapper the parser collapses or merges — a nullable `oneOf`/`anyOf` or `type: [..., "null"]`, a single-member `allOf`, an `allOf` response, field or nested-field merge — is the schema the document wrote, so the model built from what it unwraps or merges to carries the wrapper's link; a member's own stays on that member (a `$ref` member's on its component model), and a collapsed branch or member keeps its own link only when the wrapper has none. Every later pass that keeps, renames or merges models preserves the link; when `collapseJsonSuffixModels` folds `PetJson` into `Pet`, `Pet` keeps its own link as it keeps its own description, and takes `PetJson`'s only when it has none.

A Schema Object that does not become a model of its own keeps its link too. `Field.externalDocs` is the property schema's own, read like `description`: for a `$ref` with an `externalDocs` sibling (legal in OAS 3.1) the field carries the sibling's link while the referenced model keeps its own, and a bare `$ref` gives the field none — unlike `example`, a link is never taken from the referenced component. Every path that builds a field reads it: component properties, `allOf` merges, flattened `oneOf` variants, inline request bodies and responses, nested inline objects, list-envelope companions and header models. It is documentation, not shape: where two inline models are folded into one by structural agreement (`modelFingerprint`, the header-model registry, the same-named merge passes), two fields that differ only in their link are one shape, as two that differ only in `description` are. `Parameter.externalDocs` and `ResponseHeader.externalDocs` are read from the schema, as described under each. An `Enum` carries its schema's: a component enum's own, and — for an enum lifted into `spec.enums` from an inline schema on a property, parameter or response header, including array items, `oneOf` variants and a `oneOf` of string consts collapsed into one enum — that schema's. A nullable wrapper or single-member `allOf` the parser collapses carries its link onto the lifted enum by the rule above for models (the wrapper's wins; the branch's only when the wrapper has none). When several inline schemas lift to one enum name, the first lifted gives the link, as it gives the values. The link lives on the `Enum`, not on the field's or parameter's `EnumRef`.

### SdkBehavior

Source: `src/ir/sdk-behavior.ts`

Language-agnostic runtime policies consumed by emitters via `ctx.spec.sdk`. Always populated by the parser with `defaultSdkBehavior()`. Override per-SDK via `oagen.config.ts`.

```typescript
interface SdkBehavior {
  retry: RetryPolicy; // Retry status codes, max attempts, backoff strategy
  errors: ErrorPolicy; // Status code → exception kind mapping, doc URL template
  telemetry: TelemetryPolicy; // Request metrics header, request ID header
  pagination: PaginationPolicy; // Auto-page delay
  idempotency: IdempotencyPolicy; // Idempotency header name, auto-generate for POST
  logging: LoggingPolicy; // Log events and levels
  userAgent: UserAgentPolicy; // SDK identifier template, AI agent detection
  requestGuard: RequestGuardPolicy; // Misplaced-options key detection
  timeout: TimeoutPolicy; // Default timeout, env var override
}
```

Use `defaultSdkBehavior()` for canonical defaults. Use `mergeSdkBehavior(overrides)` for partial overrides (arrays replace, objects merge recursively).

## TypeRef (discriminated union)

Every type in the IR is a `TypeRef`, discriminated on the `kind` field:

| Kind        | Interface       | Example                                                              |
| ----------- | --------------- | -------------------------------------------------------------------- |
| `primitive` | `PrimitiveType` | `{ kind: "primitive", type: "string" }`                              |
| `array`     | `ArrayType`     | `{ kind: "array", items: { kind: "primitive", type: "string" } }`    |
| `model`     | `ModelRef`      | `{ kind: "model", name: "Organization" }`                            |
| `enum`      | `EnumRef`       | `{ kind: "enum", name: "Status", values?: ["active", "inactive"] }`  |
| `union`     | `UnionType`     | `{ kind: "union", variants: [...], discriminator?: {...} }`          |
| `nullable`  | `NullableType`  | `{ kind: "nullable", inner: { kind: "primitive", type: "string" } }` |
| `literal`   | `LiteralType`   | `{ kind: "literal", value: "active" }`                               |
| `map`       | `MapType`       | `{ kind: "map", valueType: { kind: "primitive", type: "string" } }`  |

### Primitive Formats

The `format` field on `PrimitiveType` carries additional type information:

| type      | format      | Semantic          |
| --------- | ----------- | ----------------- |
| `string`  | (none)      | Plain string      |
| `string`  | `date`      | ISO 8601 date     |
| `string`  | `date-time` | ISO 8601 datetime |
| `string`  | `uuid`      | UUID string       |
| `string`  | `binary`    | Binary data       |
| `integer` | (none)      | Integer           |
| `number`  | (none)      | Floating point    |
| `boolean` | (none)      | Boolean           |
| `unknown` | (none)      | Unknown/any type  |

### LiteralType

```typescript
interface LiteralType {
  kind: "literal";
  value: string | number | boolean | null;
}
```

Represents a fixed value. The `null` variant maps to language-specific null literals.

### MapType

```typescript
interface MapType {
  kind: "map";
  valueType: TypeRef;
  keyType?: TypeRef; // Defaults to string when absent
}
```

The optional `keyType` allows non-string map keys (e.g., enum-keyed maps). When absent, emitters should assume `string` keys.

A map's value schema is typed the same way an array's items are: with the owning field's name and parent model. When the value is an inline object (or an array or `oneOf` of inline objects), the parser extracts it as a model named by the parent plus the singularized field name, e.g. `layers` on `CreateDrawingRequest` → `CreateDrawingRequestLayer`, matching `shapes` → `CreateDrawingRequestShape` for array items. `additionalProperties: {}` or `true` keeps the value type `unknown`. The singular form is taken only when no sibling property of the same object would itself mint that name — an inline object, an inline enum, an inline union (the names of its object variants and whatever its other variants mint, see below), or an array or map of such (a primitive `email` beside `emails` claims nothing); otherwise array items are `<Parent><Field>Item` (`DrawingLayersItem` beside a `layer` object with different fields) and map values `<Parent><Field>Value`; if a sibling claims that name too (a property `layers_item`), the fallback continues to `<Parent><Field>ArrayItem`, then `<Parent><Field>ArrayItem2`, and so on (`<Parent><Field>MemberValue`, `…MemberValue2` for maps), taking the first name no sibling mints. One deliberate exception: when the claiming sibling is an inline object structurally identical to the items or values (same properties, required, types, nested inline schemas and enum values; `description`, `title` and `example` ignored), both fields share one model under the singular name, since one type is right for both and a duplicate would only add noise; the split happens only once the shapes diverge. The choice reads sibling names and schema content only, so document order plays no part.

Inline object variants of a `oneOf`/`anyOf` are extracted as their own models. The first keeps the field's inline name (`DrawingShape`); later ones take a const-discriminator prefix when every variant pins one (`SquareDrawingShape`). A variant with neither is named from its own content, so an SDK user can tell the variants apart and reordering them changes nothing but which one is first: its `title`, trimmed and PascalCased, as the same prefix form (`CircleDrawingShape`; a title the base name already starts with is not doubled, and a title an earlier variant already took is not reused); else the first property, in the variant's own order, that no other inline object variant of the union declares (`DrawingShapeWithSide`, `DrawingShapeWithRadius`); else, only when its property set adds nothing to another variant's, the position counter (`DrawingShape2`). Every candidate also steps around the inline names the parent's other properties mint, so a variant never overwrites another field's model: beside a `shape_with_side` object (`DrawingShapeWithSide`), the `{ side }` variant of `shape` takes the next candidate (`DrawingShape2`), and beside a `shape2` object the counter keeps counting (`DrawingShape3`); each sibling's names are read in isolation, so the choice depends on sibling names and content only. The same reservation is handed down to a union among a field's array items or map values. A `oneOf` without an explicit `discriminator:` whose every variant carries a `title` and pins the same const property is the one shape named differently: its discriminator mapping has always named each variant by its title (`Circle`, `Square`), so the extracted models carry those titles too, and the mapping is read from the same names — such a title is context-free and names one shape wherever it appears, as a component name would, so a second union beside it (at field level, or among a sibling array's items or map's values) that gives the same title a variant of the identical shape (same properties, required, types and nested schemas; `description`, `title` and `example` ignored — the rule array items already use to share a singular sibling's model) shares the model instead of stepping around it. A sibling that gives the same title a different shape reserves it, and because each side reads its siblings in isolation the decision is symmetric: when `Circle` is `{ radius }` on `shape` and `{ diameter }` on `marker`, both fall back to their context-qualified names (`CircleDrawingShape`, `CircleDrawingMarker`: the title as a prefix on the base, else a distinguishing property, else the counter) and neither keeps the bare `Circle`, with the mappings following; when the shapes are identical, both keep `Circle` and one model is emitted. The same holds at any depth of one root, not only between siblings: a title that two unions anywhere under the same root give different shapes — `Circle` as `{ radius }` on `shape` and as `{ diameter }` on `marker.shape` — is contested, decided once per document before any union is named, and every variant carrying it takes its context-qualified name (`CircleDrawingShape`, `CircleDrawingMarkerShape`), wherever in the root it sits and whichever is declared first; a union object one root holds in two places — nested under `shape` beside an earlier union that already claimed its title for that group, and again as `wrapper.marker`, where the title is a claim of its own — is read in each place, so its shape is compared with the earlier union's and the title contested when they differ; a title given one shape, or identical shapes, under a root is kept and shared. The component schemas are read as one root, since one pass collects their inline field models into one list and a named union's variants are already compared across every component; a request body, a response body, a response header, a parameter and a webhook payload are each a root of their own, and a title two such roots give different shapes is left to the passes that merge their models (the first owner keeps the name; a later shape is renamed or dropped with a warning). Should a union variant still find its name taken by a model of another shape in the list it is extracted into, the extractor keeps the first model and warns that the variant's reference resolves to it, rather than dropping the variant silently; the two are compared with the nested models each builds (`deepModelFingerprint`), so an ordinary `circle` and a variant titled `Drawing circle` that both hold a `detail` object — `{ radius }` under one, `{ diameter }` under the other, both named `DrawingCircleDetail` — are two shapes, and the warning names the nested models that differ when the parents' own fields agree. A title that coincides with another field's context-dependent model name falls back the same way. When the union has no const discriminator and every variant carries a distinct title, the first variant takes its title too (`CircleDrawingShape` beside `SquareDrawingShape`) instead of being the only one left bare. The decision reads the variants' content only, and the union TypeRef and every extractor (component fields, request bodies, inline responses, array items, map values) make it through one function, so a reference always has a model behind it. A request body that is itself a `oneOf` of inline objects follows the same rule for its const-less variants (`CreateThingRequest`, `CreateThingRequestWithB`); a variant with a const string property is still named after it, and either kind steps around a name an earlier variant of the body already took (a variant titled `Foo` beside one pinning `kind: foo` gives `FooCreateThingRequest` and `FooCreateThingRequest2`). A response that is itself a `oneOf` goes through the field extractor under the response name, so every inline object variant — const-prefixed, titled, property-named, or nullable (`type: ['object', 'null']`) — is materialized under exactly the name the union references (`GetThingResponse`, `GetThingResponseWithSide`, `SquareGetThingResponse`). Everything nested under a variant is named from the variant, never from the union's field: an inline object under the second variant is `DrawingShapeWithSideCenter` (or `SquareDrawingShapeCenter` under a titled one); a multi-type variant such as `type: ['object', 'array']` keeps its other types beside the model (`union[model, array]`), and the inline items of that array member are `<Variant>Item` (`DrawingShapeWithSideItem`, with nested objects `DrawingShapeWithSideItemChild`); any other non-object member is named `<Variant>Value` (an inline enum, for instance). If a property of the variant already claims that model name (`item`, or `items`, which singularizes to the same `<Variant>Item`), the member falls back to `<Variant>ArrayItem` / `<Variant>MemberValue`, then `<Variant>ArrayItem2`, `<Variant>ArrayItem3`, and so on. A variant that admits null (`['object', 'null']` or `nullable: true`) keeps its `nullable` wrapper around the model.

Every other variant of an inline `oneOf`/`anyOf` — one that is neither a `$ref`, an inline object, nor `type: 'null'` — is typed and extracted under a context decided by one function, which the union TypeRef, every extractor and the sibling-name reservation all read, so a reference always has a model behind it. An array or map variant is typed under `<field>_item` / `<field>_value`, so its inline items or values are `<Parent><Field>Item` / `<Parent><Field>Value` (`CreateThingRequestFItem` for the items of an array variant of `f`), never the name an object variant of the same union keeps. A variant that would mint a model or enum name under the field's own context — a union nested under the variant (its inline object variants are named from the field's name as the outer ones are, so its first one would otherwise take the outer variant 0's name), a nullable wrapper around an inline object (`oneOf: [{ … }, { type: 'null' }]`), an `allOf`, an inline enum or a `oneOf` of string consts — keeps the field's context when nothing it mints there is claimed, and is otherwise typed under `<field>_variant_<n>`, n its 1-based position among the non-null variants, as a named union's non-object variants are: beside an object variant `GetNoteError400`, the variants of a nested union are `GetNoteError400Variant2` and `BGetNoteError400Variant2`, a nullable object or an `allOf` is `GetNoteError400Variant2`, an inline enum is `GetNoteError400Variant2`; beside only a primitive, a nested union still names its variants `GetNoteError400` and `BGetNoteError400`, and an inline enum keeps `GetNoteError400`. Only context-dependent names take part: a nested `oneOf` whose every variant carries a `title` and pins the same const property names its variants by those titles (`A`, `B`), which are the same under every context, so it keeps the field's context and is materialized under the titles — while one of its variants whose title is already taken falls back to a context-qualified name (`AGetNoteError400`) and steps with it. A variant typed under its context steps around every name claimed at that point — the sibling-minted and caller-reserved names the field's own variants step around, the union's inline object variants and their children, every name an earlier variant minted, and a context-free title an earlier variant kept for a different shape (one kept for the identical shape is shared, as between sibling fields) — so a nested titled variant whose title is already a sibling field's model (`HolderA` beside `Holder.a`), an earlier variant's model (`HolderShapeVariant2`) or an earlier nested variant's title of another shape takes its context-qualified name (`HolderAHolderShape`, `AHolderShape`) exactly as a field-level titled variant does beside the same sibling, and the union never exposes the sibling's fields. A name is claimed when a sibling property mints it, an inline object variant of the union takes it, an object variant's own property mints it, or an earlier variant of the union minted it; when the chosen context still mints a claimed name it steps on as an array's items do beside a claiming sibling (`<field>_array_item`, `<field>_array_item2`, … for an array or map variant; `<field>_variant_<n>_value`, `<field>_variant_<n>_member_value`, … for the rest). The rule applies wherever an inline union is typed — a component field, a request body (a `oneOf` body's inline object variants keep their body names, see below; its other variants follow this rule, and a body typed by `schemaToTypeRef` alone, such as an `anyOf` or an array, has every inline model it references materialized the same way), an inline 2xx response, an error body, a discriminated `allOf` + `oneOf` variant's field, array items and map values — and to a nested union's own variants in turn (`GetNoteError400Variant2Variant2` for a union nested two levels down).

**`properties` beside a composition.** JSON Schema applies every keyword of one schema at once, so an inline schema that writes `properties` beside an `allOf`, `oneOf` or `anyOf` that types it — `{ properties: { id }, allOf: [{ $ref: Pet }] }` is a `Pet` that also has `id`; `{ properties: { id }, oneOf: [pet, note] }` is one of `pet` or `note` with `id` in either case — is read as the composition carrying the properties, wherever it sits: a field, array items, map values, a request body, a response body, a list envelope's items, a parameter, a header, a webhook payload. An `allOf` gains the schema's own `properties` and `required` as its first member, so the augmentation of a `$ref` member (`HolderThing { id, name }`), a model merged from inline members, or a single member unwrapped carries them, the schema's own first. Each inline object variant of a `oneOf`/`anyOf` — `type: 'object'`, no `type`, or a type list naming `object`, so a nullable or multi-typed object variant included — gains them the same way (`HolderThing { id, name }`, `HolderThingWithText { id, text }`), the schema's own declaration kept where the variant declares the same property and the `required` names the union of both lists; the union keeps every variant. Every other variant is typed as written: a `$ref` names a component the parser never merges properties into; a primitive, array or enum is no object, so `properties` constrains nothing in it; a nested composition or a nullable union wrapper is left to its own variants. The parser warns once per union, with the field's context, for the variants that may be objects and did not take the properties (a `$ref`, an `allOf`, a nested union, a map, a nullable wrapper around an object): `[oagen] Warning: \`properties\` beside \`oneOf\` are carried into its inline object variants only; variant 1 is typed as written, without them (context: GetThingResponse.mixed)`. An `allOf`or`oneOf`of bare limits beside`properties`does not type the schema, which stays the object it is with the limits conjoined (see Constraints). Where the composition is merged into one model — an`allOf`as a field, as array items or as a response body — earlier members win on a shared property name, the schema's own first, so an own`kind`enum beside a member's plain`kind`stays the enum at every site. Component schemas keep their own rule: a`oneOf`written beside`properties`under`components.schemas` is the object model (see Named unions).

## AuthScheme

```typescript
type AuthScheme = { description?: string; schemeName: string } & (
  | { kind: "basic" }
  | { kind: "bearer" }
  | { kind: "apiKey"; in: "header" | "query" | "cookie"; name: string }
  | { kind: "oauth2"; flows: Record<string, unknown> }
);
```

Emitters use `AuthScheme` to generate authentication configuration and client constructors. The `cookie` variant supports cookie-based API key authentication.

`schemeName` is the key under `components.securitySchemes`, spelled exactly as in the document, and `description` is present only when the document declares one; entries keep the document's order. The requirements under `ApiSpec.security` and `Operation.security` refer to the same key, so an emitter joins a requirement to its scheme with `spec.auth?.find((a) => a.schemeName === requirement.schemeName)`. The optional chaining matters: `auth` is `undefined` when the document declares no scheme the IR can represent, and a requirement can still name a scheme that was omitted (see below), so a missing match means "no SDK-level auth is known for this operation", not an error.

HTTP scheme names are matched case-insensitively (`Bearer`, `bearer`, and `BEARER` all yield `kind: "bearer"`). Security schemes the IR cannot represent (other `http` schemes such as `digest`, plus `openIdConnect` and `mutualTLS`) are omitted from `auth`, and the parser prints an `[oagen] Warning:` diagnostic naming the scheme.

## HttpMethod

```typescript
type HttpMethod =
  "get" | "post" | "put" | "patch" | "delete" | "head" | "options" | "trace";
```

All standard HTTP methods are supported. Emitters should handle `head`, `options`, and `trace` appropriately (e.g., HEAD returns no body).

## PaginationMeta

```typescript
type PaginationStrategy = "cursor" | "offset" | "page" | "link-header";

interface PaginationEndOfIteration {
  kind: "hasMore" | "totalPages" | "totalCount";
  path: string; // Dotted path from the response root, like dataPath: "has_more", "pagination.totalPages"
}

interface PaginationMeta {
  strategy: PaginationStrategy;
  param: string; // Query param that selects the page (e.g., "after" for cursor, "offset" for offset, "page" for page)
  limitParam?: string; // Page-size param (offset and page strategies, e.g., "limit")
  pageStart?: number; // First page number (page strategy only): the param's default, else its minimum, else 1
  dataPath?: string; // JSON path to the data array (e.g., "data", "results") — undefined means the response IS the data
  dataDescription?: string; // The data array property's own description, when it declares one
  itemType: TypeRef; // Type of each item in the paginated list
  envelopeFields?: Field[]; // Every envelope property besides the data array, in document order
  endOfIteration?: PaginationEndOfIteration; // Response field that ends the iteration, when one is recognized
}
```

Present on `Operation` when pagination is detected. The `strategy` discriminant tells emitters how an auto-paging iterator reaches the next page:

| Strategy      | Detected from                                                  | Next page                                                                       |
| ------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `cursor`      | a cursor-like query param (`cursor`, `after`, `page_token`, …) | send the cursor the previous response returned in `param`                       |
| `offset`      | `offset` or `skip` plus a page-size param                      | add the number of items received to `param`; send the page size in `limitParam` |
| `page`        | `page`, `page_number` or `page_num` plus a page-size param     | send `pageStart` first and add exactly one per request                          |
| `link-header` | never detected — set through an override                       | follow the RFC 5988 `Link: <…>; rel="next"` response header (e.g., GitHub API)  |

A cursor param wins over an offset param, which wins over a page param, when an operation declares more than one; a page or offset param without a page-size param (`limit`, `page_size`, `per_page`, `size`, `count`) is not pagination.

`pageStart` is set for the `page` strategy only: the page parameter's integer `default`, else its `minimum`, else 1 (`?page=0` APIs declare `default: 0` or `minimum: 0`), or whatever an override sets. The keywords are read from the parameter's schema as written — the schema's own value, then the component a `$ref` names, then `allOf` members in declaration order, then the non-null variant of a nullable wrapper — so a `default: 0` behind `allOf: [{ $ref }]` or a `$ref` into `components.parameters` still counts. Emitters read `pageStart` instead of re-deriving the base.

Every iterator stops on an empty page. `endOfIteration`, when present, lets it stop one request sooner:

- `hasMore` — a boolean that is `false` on the last page.
- `totalPages` — an integer count of pages; stop once the pages fetched so far reach it. Under `page` that is `page - pageStart + 1 >= totalPages` (`page >= totalPages` for a 1-based API, `page + 1 >= totalPages` for a 0-based one); under `offset` it is `floor(offset / limit) + 1 >= totalPages`.
- `totalCount` — an integer count of items; stop once the items received so far reach it.

It is detected from a recognized envelope — a boolean `has_more`/`hasMore`/`has_next`/`hasNext`/`has_next_page`/`hasNextPage`, an integer `total_pages`/`totalPages`/`page_count`/`pageCount`, or an integer `total`/`total_count`/`totalCount`/`total_items`/`totalItems`/`total_results`/`totalResults` — at the top level first, then one level down inside each companion object whose name says it is pagination metadata (`meta`, `pagination`, `page_info`, `cursor`, …; inline, `$ref`, `allOf`, or a nullable wrapper) — a `stats.total` beside `pagination.page` is not the list's size — and the path follows the `dataPath` convention. When several candidates exist, `hasMore` beats `totalPages`, which beats `totalCount`. List-envelope recognition shares that list of names, so an envelope whose only companion is a stop field (`{ data, hasMore }`) is unwrapped like any other; before this list existed only `has_more` and the `total…` names (through the metadata substrings) marked an envelope, so `{ data, hasMore }`, `{ data, hasNext }`, `{ data, pageCount }` and the other spellings now unwrap where they used to be a plain response model, and an operation returning one without paging parameters gets the envelope fallback (`strategy: 'cursor'`, `param: 'after'`) as a `{ data, has_more }` always has.

The `dataPath` is dynamically detected from the response envelope — when `undefined`, emitters should treat the entire response as the data array or use their own default.

When the parser recognizes an inline list envelope — one array property plus a companion that looks like pagination metadata — `Operation.response` becomes the bare array, and `envelopeFields` keeps everything else the envelope carries. The array property is an array in any spelling, and two `allOf` declarations of it — one nullable, one not; one with `items`, one with limits alone — merge as the arrays they wrap (the later `items` when they narrow, the earlier otherwise, `null` admitted when either side admits it): `type: 'array'`, `items` with no `type`, or either under a nullable wrapper — `type: ['array', 'null']`, OAS 3.0 `nullable: true`, or a `oneOf`/`anyOf` with a `null` variant, with or without `items` beside it — in which case `response` is `nullable<array<Item>>` while `itemType` is still the element (`ListEventsItem[] | null`, `dataPath: 'data'`). Its items, whatever their shape, are typed as `<Op>Item` (see Inline model naming). `envelopeFields` keeps everything else the envelope carries: the pagination companion (`list_metadata`, `pagination`, `has_more`, `total`, …) and any discriminant such as `object: "list"`. Each entry is an ordinary `Field` (wire name, type, `required`, description), so `dataPath` + `itemType` + `envelopeFields` together describe the full shape of what the endpoint returns, and an emitter can both type the response and read the page details it needs for the next request:

```typescript
// GET /customers?page=&limit= → { customers: Customer[] ("The customers on this page."), pagination: { page, totalPages } }
op.pagination = {
  strategy: "page",
  param: "page",
  limitParam: "limit",
  dataPath: "customers",
  dataDescription: "The customers on this page.",
  itemType: { kind: "model", name: "Customer" },
  envelopeFields: [
    {
      name: "pagination",
      type: { kind: "model", name: "Pagination" },
      required: true,
    },
  ],
  endOfIteration: { kind: "totalPages", path: "pagination.totalPages" },
};
```

A companion that is an inline object is lifted to a model. The same envelope recurs on every list endpoint of an API, so copies that agree structurally share one model named from the property alone (`list_metadata` → `ListMetadata`, `pagination` → `Pagination`) rather than one per operation as list items are (`ListUsersItem`). The bare name is taken only where it cannot change another type's shape. A copy collapses onto a target only when the target admits every value the copy can hold: the same fields with the same types, where the target may be looser (optional where the copy requires, nullable where the copy is not) but never stricter. When a component model of that name exists, the copies it admits collapse onto the component as written; otherwise the most common shape becomes the target. Any other copy keeps its operation-qualified name (`ListUsersPagination`). An inline enum in a companion is qualified by operation exactly like a parameter enum (`ListUsersSortOrder`). Companions declared through an `allOf` `$ref` branch are resolved against the component schemas, and a companion declared by more than one branch merges both declarations. Models and enums reached only through `envelopeFields` count as referenced for emission, service assignment, compat scoping, and the differ's request/response direction.

The data array property's own description, when it declares one, is kept beside `dataPath` as `dataDescription`, so an emitter documenting what a list method returns (an `@returns` tag, say) reads it from the IR like the companions' descriptions rather than from the document. As with a `Field`'s `description`, it is the property's text and never the item schema's; an inline item object's description is on the lifted item model.

`envelopeFields` is absent when the response is a bare array, when the response is a `$ref` to a component schema (the wrapper model itself carries the companions), or when pagination was inferred from query parameters alone. `dataDescription` is absent in the same cases — the wrapper model's own data field carries the description — and whenever the data property declares none.

### Overriding detection

An `x-pagination` extension on the Operation Object, or the `pagination` entry of the operation's `operationHints["METHOD /path"]` in `oagen.config.ts`, states the pagination explicitly when the name-based guess is wrong. Both take the same object (`PaginationHint`), and precedence is per field — config hint, then `x-pagination`, then detection — so `{ strategy: "page" }` alone corrects the strategy and keeps the detected parameters, envelope and end-of-iteration field.

```yaml
# In the spec, for authors who can annotate it
paths:
  /pets:
    get:
      x-pagination:
        strategy: page # cursor | offset | page | link-header | none
        param: page # must be a query parameter of the operation
        limitParam: limit
        pageStart: 1 # page strategy only; defaults to the param's default, else minimum, else 1
        dataPath: pets # resolved against the response; the array's element type becomes itemType
        endOfIteration: { kind: totalPages, path: pagination.totalPages }
```

```ts
// In oagen.config.ts, when the spec cannot be changed
export default {
  operationHints: {
    "GET /pets": { pagination: { strategy: "page" } },
  },
};
```

`strategy: "none"` turns pagination off for the operation. The decision is made before the response is classified, so a list envelope is not unwrapped: the body becomes one plain response model carrying every field (`pets`, `pagination`, …), exactly as a non-list body does, and nothing about the wire shape is lost.

An explicit `dataPath` is resolved against the primary response (the lowest 2xx with a body, the one `Operation.response` describes — not whichever 2xx is declared last) and the element type of the array it lands on becomes `itemType`, so a wrapper with `pets: Pet[]` iterates `Pet` rather than the wrapper. The IR is consulted first — the detected data array, an envelope companion's fields, or the response model's fields — so the item model the parser already created is reused; the document (through a root `$ref` wrapper, `allOf` members and nullable wrappers) is read only when the path crosses a model not yet materialized (an array component's, say), and inline items found that way — a plain or nullable object, the object variants of a union, the objects of a nested array or map, and whatever those reference in turn — are materialized under a name derived from the path as the inline extractor names a field's items (`result.items` → `<Op>ResultItem`, `records` → `<Op>Record`), never the bare `<Op>Item` the envelope's own data array owns, so the item type never names a model the parser did not create. Such an item type is a reference nothing else in the IR holds, and the parser's later passes reach it on its own: an inline enum it is (or holds) is promoted to `spec.enums` under the path-derived name, stepping past a component enum with other members as a header enum would; a `…Json` model it names follows the Json-suffix fold; and an unresolved model in it is reported under `pagination.itemType`.

`param` is resolved in this order: the override's own, else the first query parameter the operation declares under the strategy's own names (`page` for `page`, `cursor`/`after`/… for `cursor`, `offset`/`skip` for `offset`), else the detected one — so `{ strategy: 'page' }` on `GET /pets?page` drives `page` even where the envelope fallback had guessed `after`. The resolved `param` and `limitParam`, not only explicit ones, must be query parameters the operation declares.

An explicit `dataPath` that names another array than the one the parser would unwrap (`{ data, result: { items }, total }` with `dataPath: 'result.items'`) means detection was wrong for the operation, so the envelope is kept as a wrapper, exactly as `strategy: 'none'` keeps it: `response` is the wrapper model (what the wire returns), `dataPath` says where the items are in it, `itemType` is their type, and `envelopeFields` is absent since the wrapper carries the companions; the wrapper's stop field is still read (`total` → `endOfIteration`), also when the override is what creates the iterator — no paging parameter recognized, say a custom `param: 'p'` — rather than correcting a detected one. The array may sit under a nullable wrapper of any form — `type: ['array', 'null']`, OAS 3.0 `nullable: true`, `oneOf: [{ type: 'array' }, { type: 'null' }]`, a nullable `$ref` to an array component — and the document is read through the same wrappers the IR walk reads through, so whether the path reaches an array is decided once, the same way, before the body is classified and when its items are typed. A `dataPath` that restates the detected one changes nothing, and one that reaches no array leaves the envelope unwrapped and is ignored with a warning. Because a kept wrapper is not a recognized envelope, such an override needs a strategy from somewhere — its own, or the operation's query parameters. Whether an override can apply at all is decided before the response is read, against the pagination the query parameters alone yield (the envelope fallback's invented `after` never makes one usable), so an override that is rejected leaves the response exactly as detection reads it. `dataDescription` survives an override that keeps the detected array, and the stop field beside a nested array an override selects (`pagination.has_more` next to `pagination.items`) is still read; a stop field wrapped in a nullable `oneOf` (`[{ type: 'boolean' }, { type: 'null' }]`) or behind a `$ref`, however the two alternate, is read like one declared with a type list, and a component that refers back to itself (`Flag: { oneOf: [{ $ref: Flag }, { type: 'null' }] }`) ends the walk rather than looping on it, as a stop field or as any other companion.

An override that cannot be applied — an unknown strategy, a strategy with no `param` from any source, a resolved `param` or `limitParam` the operation does not declare as a query parameter, a `dataPath` that does not reach an array in the response, a malformed field — is reported as an `[oagen] Warning:` and ignored, leaving the detected metadata in place; an unknown key is skipped with a warning. `envelopeFields` always comes from the response.

## Service & Operation

Service names are derived from OpenAPI tags when present — the first tag on an operation is converted to PascalCase (e.g., `tags: ["multi-factor-auth"]` → service `MultiFactorAuth`). When no tag is present, the parser falls back to a path segment (e.g., `/organizations/{id}` → `Organizations`), skipping the API root the document's untagged operations sit under. Each untagged path contributes its leading literal segments through the last API marker — `api`, `rest`, or a version such as `v1`, `2.0` or `2010-04-01` — and the root is the longest marker-terminated prefix shared (compared verbatim) by every contribution that no other contribution extends, so a document whose paths all start with `/api/v1/` groups `/api/v1/notes` under `Notes` rather than collapsing the whole API into one `Api` service, and `/wiki/rest/api/content` lands in `Content`. A path that stops short of that root — `/api/openapi.json` or `/api/admin/users` beside `/api/v1/notes` — skips only its own `api` (`OpenapiJson`, `Admin`) and leaves the root at `api/v1` for the rest, so `/api/v1/notes` stays `Notes`; only a second version, `/api/v2/…` beside `/api/v1/…`, shortens the root to `api`, which keeps the versions apart as `V1` and `V2`. The service is named from the first literal segment after the root, so `/v1/notes` and `/v1/{teamId}/notes` share `Notes`, and a custom method written after a colon (`/v1/pets:batchGet`, `/v1/pets/{petId}:adopt`) is read as its segment followed by the verb, so both land in `Pets`; a path with nothing literal after the root (`/api` itself, `/api/{id}`) keeps its first segment, `Api`. A path with no marker at all (`/health`, `/openapi.json`) sits outside the root, keeps its own first segment, and does not switch the root off for the rest of the document. A shared prefix that carries no marker is kept whole, since a module prefix every path shares (`/user_management/users`, `/user_management/invitations` → `UserManagement`) is the service, not noise; and `/v1/…` beside `/v2/…` has no shared root, so the versions stay separate services. Tagged operations and path items without an operation take no part. The path-prefix split that carves a tagged service into one per first segment (`/organizations` and `/organization_domains` both tagged `organizations` → `Organizations` and `OrganizationDomains`) is decided over the tag's own operations alone, from the grouping before any service is split: a tag whose operations all sit under one first segment keeps them together even when that segment is not the tag, so `/api/v1/notes` tagged `notes` stays in `Notes`, not `Api`, whatever untagged operations `Notes` picked up by path. An untagged operation keeps the service its path named — it is never moved by a split, and it neither causes nor prevents one — so `/notes` and `/api/v1/notes` meet in `Notes` instead of the latter moving to `Api`, and the collision rules below tell their names apart. A split-off part named like an existing service — another tag's, or a path-named one — joins it, and the operations it brings do not re-split that service. Fallback operation names skip the root and the service segment the same way, so `/api/v1/notes` is `Notes.list`, never `Notes.listV1Notes`; when two path-named operations still share a name in one service and their paths differ only by parameters, the parameters qualify them (`/v1/notes` → `Notes.list`, `/v1/{teamId}/notes` → `Notes.listByTeamId`; see the collision rules under Operation below). Without a root — a root-less document, a path outside the root, or a tagged operation — services are exactly what they were before this rule, and so are fallback names up to those collision rules: an untagged `/{tenant}/users` stays `Default.listUsers`. Emitters can further remap service names via an overlay (e.g., `MultiFactorAuth` → `Mfa`) to match existing SDK class names.

`Service.description` comes from the document's top-level `tags` list, matched by name: a tag entry applies to the service whose PascalCase name its `name` converts to, so `user-management`, `User Management`, and `user_management` all map to `UserManagement`. A service whose own name is a declared tag is described by that tag alone — its description when it has one, nothing otherwise — so another tag's wording is never borrowed for it (operations tagged `api_keys` that the path-prefix split merges into `UserManagement` do not label it "API keys"). A service whose own name is not declared, which is what the split produces when it carves `OrganizationDomains` out of operations tagged `organizations`, inherits the description of the first described tag its operations carry. The key is omitted when neither rule yields a description, including for path-named services whose operations have no tag. Malformed `tags` values (a non-array, `null` entries, non-string names) are skipped rather than failing the parse.

`Service.externalDocs` is the tag's `externalDocs` (see [ExternalDocs](#externaldocs)), resolved by the same rule through the same code path: a service named after a declared tag takes that tag's link or nothing, and a split-off service inherits the link of the first linked tag its operations carry. Each field is chosen independently, from the first tag that gives it — among the tags a split-off service inherits from and among several document tags that normalize to one service name — so the description and the link need not come from the same tag, and adding a link to a tag never changes which description a service shows. A tag entry whose `externalDocs` is unusable keeps its description and gives no link.

`Operation.externalDocs` is the operation's own `externalDocs`, present only when it declares a usable one. A Path Item Object has no `externalDocs` field, so an operation that declares none carries none.

An operation's `callbacks` are not read; a `paths` operation that declares any is warned about once, by name, and parsed as if it declared none. See [Webhook](#webhook) for the rule, which covers a `webhooks` operation too.

An operation carries its OpenAPI `summary` and `description` in two fields, each read from the Operation Object and, when the operation declares none with content, from the Path Item it sits on — OpenAPI defines a Path Item's `summary` and `description` as applying to every operation on it. The two fall back one by one: an operation with a `summary` of its own and no `description` shows its own `summary` over the Path Item's `description`, and an operation with both shows only its own. `Operation.description` is the combined doc text of the two resolved texts: `summary + "\n\n" + description` when both have content, or whichever one has content (a summary identical to the description is not repeated). An empty or whitespace-only `summary` or `description` is treated as absent at either level — `summary: "List pets"` with `description: ""` yields `description: "List pets"`, and `summary: ""` on an operation takes the Path Item's — and text that has content is kept verbatim, surrounding whitespace included. An emitter that prints `description` as the doc comment therefore sees the same text whether the document put the text on the operation or on its Path Item, and whether or not it used a summary. `Operation.summary` is the resolved `summary` alone and is present only when one of the two levels has content, so an emitter that wants a one-line label (and the description without it) reads `summary` rather than guessing whether the first paragraph of `description` is one. When a doc URL base is configured, relative links are expanded in `summary` exactly as in `description`.

An operation without an `operationId` is named from its method and path (`GET /orgs/{id}/teams` → `listTeams`), and that name is only as unique as the path words it was built from. Within a service, a name taken from an `operationId` is kept as written, and path-derived names that collide with each other or with it are qualified until every path has a name of its own; two operations on one path share a name only when both are path-named and their methods take the same CRUD verb (PUT and PATCH both `update`); a path-named operation of another verb takes the name it has without the action rule (`POST /pets/bulk-delete` beside `DELETE /pets/bulk-delete` is `createBulkDelete`), numbered when that name is held on the path too (a path-named PATCH beside `operationId: updatePet` on the PUT is `updatePet2`), and an `operationId` reused on one path is numbered with a warning. Qualifiers are tried in order, each on whatever still collides, every one through one rule. A qualifier is added only when it tells the colliding paths apart, compared as noun phrases so a word in either number is one word: `Teams` sits in both `/org/teams/members` and `/org/teams/{teamId}/members`, so they are `listMembers` and `listMembersByTeamId`, never `listMembersTeams` and `listMembersTeam`. A qualified name another operation in the service already has is skipped for that operation and the next qualifier is tried, so a number never lands on a name a qualifier produced: `/org/members/archived` beside `/org/teams/archived` and `/org/archived_members` is `listArchived`, `listArchivedTeams` and `listArchivedMembers`, never `listArchivedMembers2`. Operations a qualifier does not tell from each other take one spelling and stay together for the next one: `/orgs/{orgId}/groups/members` and `/orgs/{orgId}/groups/{groupId}/members` beside `/orgs/teams/members` are `listMembersGroups` and `listMembersGroupsByGroupId`. A qualifier never puts the same word twice in a row into a name (word for word on the camelCase boundary, each word compared by its singular form): one the name already ends with is not repeated, so `listNotes` never becomes `listNotesNotes`, nor `listNotesNote` for `/orgs/notes/{id}/notes`, and one that repeats a word itself is collapsed, so `/org/analytics/analytics/teams` next to `/org/teams` yields `listTeamsAnalytics`. Every qualifier skips the API root and the service segment just as the name itself does, so `DELETE /api/v1/notes/all` in `Notes` is `deleteAll`, never `deleteAllV1Notes`. The order: first the resource noun; then the path segments between the service and the resource, each singular when a path parameter follows it, as the resource of an item operation is (`GET /users/{id}/legacy/factors` next to `GET /users/{id}/factors` becomes `listFactorsLegacy`, and `GET /store/cats/{id}/toys/{toyId}` next to `GET /store/dogs/{id}/toys/{toyId}` becomes `getToyCat` and `getToyDog`); then `By<Param>` for each path parameter the colliding paths do not all share, in path order, when those are what tell the paths apart (`GET /v1/notes` keeps `list` while `GET /v1/{teamId}/notes` becomes `listByTeamId`, `GET /users/teams` keeps `listTeams` while `GET /users/{id}/teams` becomes `listTeamsById`, `/orgs/{orgId}/{teamId}/members` beside `/orgs/members` gains `ByOrgIdByTeamId`, and `GET /api/notes/{noteId}` keeps `get` while `GET /api/{teamId}/notes/{noteId}` becomes `getByTeamId`, the shared `noteId` adding nothing, and a parameter that carries a custom method contributes the parameter alone: `GET /v1/pets/{petId}:history` beside `GET /v1/{orgId}/pets/{petId}:history` becomes `getPetHistoryByOrgId`); then the API root words a path skipped beyond those the colliding rooted paths all skipped, when they sit under different lengths of the document root — the one place a root word belongs in a name: `GET /api/notes` keeps `list` while `GET /api/v1/notes` becomes `listV1`, and a root-less path takes no part; then the resource noun the plain name left off because it names the service, when the colliding paths do not all drop the same one — this is what tells a path-named operation from an `operationId` it collides with, since that name is never rewritten and the parameters may have nothing to add: `GET /api/notes` beside `operationId: list` on `GET /api/{teamId}/notes` is `listNotes`, and `list` stays with the `operationId`, while the item `GET /api/notes/{noteId}` beside `operationId: get` is `getNote`, the noun singular as an item operation's resource is; then, for an item operation whose singular name none of those could tell apart, the plural it had before singularisation (`GET /store/pets/{id}` is `getPet`, and so is `operationId: getPet` on `/store/featured/{id}` or path-named `GET /store/pet/{id}`, so it becomes `getPets`) when no operation outside its group has that name — an `operationId`-named operation, an action, a singleton of one item (`GET /store/pets/{id}/status` is `getPetStatus`) and a name a qualifier has extended have no plural, and members that would all take the same plural are numbered instead, on the plural when an `operationId` is what they collide with (`/store/pets/{id}` and `/store/Pets/{id}` beside `operationId: getPet` are `getPets` and `getPets2`); and finally, when no qualifier is left, a numeric suffix (`list2`, `list3`, …) for paths that flatten to the same words (`/v1/{userId}/notes` and `/v1/{user_id}/notes`, or `/notes` and `/api/v1/notes`, which differ only by the root) or whose every qualified name is taken (`/api/notes` beside `operationId: list` on `/api/{teamId}/notes` and `operationId: listNotes` on `/api/{orgId}/notes` is `list2`, never `listNotes2`). A name that already ends in a digit — the version a root word gave it, a path word such as `top10`, or an `operationId` such as `getV2` — takes the number behind `No`, so that it cannot be read as part of the number the name ends with: `GET /api/v1` beside `GET /api/v1/` is `listV1` and `listV1No2`, never `listV12`, which would read as version 12, `GET /api/v1/{userId}/notes` beside `GET /api/v1/{user_id}/notes` under a versionless `GET /api/{userId}/notes` is `listV1` and `listV1No2`, and `GET /pets/top10` beside `GET /pets/top10/` is `listTop10` and `listTop10No2`; a number on one path is spelled the same way, so a path-named PATCH on `/store/top10/{id}` beside `operationId: updateTop10` on the PUT is `updateTop10No2`. For the plain name, an `operationId`-named operation outranks a path-named one, then the path that skipped the shorter root (`/health` or a tagged `/notes` keeps `list` over `/api/health` or `/api/v1/notes`, exactly as without the root), and otherwise the lexically first path wins, so the outcome does not depend on document order. The suffix is silent for a path-derived name, like a hashed inline model name; when the document itself reuses an `operationId` within a service, the later path is suffixed with a `[oagen] Warning:`, since that changes a name the author chose.

```typescript
interface Service {
  name: string; // e.g., "Organizations"
  description?: string;
  externalDocs?: ExternalDocs; // The document tag's link, by the same rule as description
  operations: Operation[];
}

  name: string; // e.g., "listUsers", "getUser", "createUser"
  summary?: string; // The document's summary alone; only when it has non-whitespace content
  description?: string; // summary + "\n\n" + description when both have content, else whichever does
  externalDocs?: ExternalDocs; // The operation's own externalDocs, when usable
  httpMethod: HttpMethod; // All 8 standard HTTP methods
  path: string; // e.g., "/organizations/{id}"

  requestBodyEncoding?:

  requestBodyRequired?: boolean; // Whether the caller must send the body; present exactly when requestBody is
  requestBodyContentType?: string; // The essence of the media type requestBody was read from — send it as Content-Type; set exactly when requestBody is
  requestBodyContentTypes?: string[]; // Media types the request body declares, in document order (only when any exist)
  requestBodyContents?: RequestBodyContent[]; // A type per media type above, same order (only when any exist)
  response: TypeRef; // Primary response: the lowest 2xx with a typed body, else the lowest declared 2xx/3xx; unknown when there is none
  responseHeaders?: ResponseHeader[]; // Headers declared on the primary response (only when any exist)
  responseDescription?: string; // The primary response's description (only when it has content)
  responseContentTypes?: string[]; // Media types the primary response declares, in document order (only when any exist)
  responseContents?: ResponseContent[]; // A type per media type above, same order (only when any exist)
  successResponses?: SuccessResponse[]; // Every declared 2xx and 3xx response; only when more than one is declared
  errors: ErrorResponse[];
  defaultResponse?: DefaultResponse; // The `default` response (only when declared)
  rangeResponses?: RangeResponse[]; // `1XX`–`5XX` range responses, in declaration order (only when any exist)
  pagination?: PaginationMeta;
  injectIdempotencyKey: boolean; // true when spec declares Idempotency-Key header
  deprecated?: boolean;
  async?: boolean;
  tags?: string[]; // The operation's tags in document order, entries that are not non-empty strings dropped; only when at least one remains
  security?: SecurityRequirementSet[]; // Per-operation requirements; undefined inherits ApiSpec.security
  parameterGroups?: ParameterGroup[]; // Mutually-exclusive parameter groups from x-mutually-exclusive-parameter-groups; see ParameterGroup in src/ir/types.ts

interface SecurityRequirement {
  schemeName: string; // Matches AuthScheme.schemeName in ApiSpec.auth
  scopes: string[];
}

// One alternative: every scheme in the set is required together.
type SecurityRequirementSet = SecurityRequirement[];
```

`security` mirrors the OpenAPI document instead of flattening it. Each requirement object in the document becomes one `SecurityRequirementSet` whose schemes must all be satisfied together ("all of"); the list of sets is satisfied by any one of them ("either of"); an empty set is an alternative that needs no credentials, which is how a document marks authentication optional. The field therefore distinguishes cases a flat list could not:

| Document                                            | `Operation.security`                  | Meaning                                              |
| --------------------------------------------------- | ------------------------------------- | ---------------------------------------------------- |
| no `security` key                                   | `undefined`                           | inherit `ApiSpec.security`                           |
| `security: []`                                      | `[]`                                  | no authentication                                    |
| `security: [{ userToken: [] }, { partnerKey: [] }]` | `[[{ userToken }], [{ partnerKey }]]` | either scheme                                        |
| `security: [{ userToken: [], partnerKey: [] }]`     | `[[{ userToken }, { partnerKey }]]`   | both schemes together                                |
| `security: [{ userToken: [] }, {}]`                 | `[[{ userToken }], []]`               | `userToken`, or nothing (authentication is optional) |

To resolve what an operation accepts, take `op.security ?? spec.security`; a result of `undefined` means the document declares no requirements at all. The same list shape applies to `ApiSpec.security`.

The differ compares security on what a request actually carries, resolved the same way on each side (`[]` when neither the node nor its document declares a list), and reports a difference as `securityChanged: true` on the `operation-modified` or `webhook-modified` change with `oldSecurity`/`newSecurity` beside it, present exactly when the flag is. A node that declares no list on either side inherits twice and is not reported: a moved document default is the document-level `security-changed` change's to report, so a document that moves to what an operation already declared (its override vanishing with it) is no change to that operation. Lists are compared as sets of alternatives, each a set of schemes with scopes as sets, so order and repetition do not count, and `security: []`, a lone anonymous alternative (`[{}]`) and nothing declared anywhere are the same thing: no authentication. The classification is read from the node's side of the wire, by one rule applied in each direction (`classifySecurityChange` in `src/differ/security.ts`): for an operation, a caller built for the old list must still satisfy the new one — breaking when some old alternative satisfies no new one (a scheme or scope now required, an alternative removed, an anonymous alternative withdrawn), additive when every old alternative still passes (an alternative added, a scheme or scope no longer needed, authentication made optional); for a webhook, the handler built for the old list must still find what it checked for in whatever the sender now presents — breaking when some new alternative carries no old one (a credential the sender stops presenting, an alternative it may now use that the old list never offered), additive when every new alternative still carries some old one (a credential the sender starts carrying beside the old ones, an alternative withdrawn). The document-level change is read from the caller's side, and from the receiver's side as well when a webhook in either document inherits the default, breaking if either side breaks. Every security change is mirrored into `behaviorChanges` as a `security-changed` entry naming the node (`document`, `operation` or `webhook`) with the two lists and the security change's own classification, beside the deprecation and parameter-default entries collected there. `tags` differing — compared in document order, an absent key as an empty list — is `tagsChanged: true` on the same changes with `oldTags`/`newTags` beside it, additive always and not mirrored into `behaviorChanges`. That flag can only ever carry an edit that leaves the operation in a service of the same name, because operations are matched by name within a service: the parser groups an operation by the document's first tag entry and then the path-prefix split (see Service above), so a first-tag change that the split files back under the same path-named service is a `tagsChanged`, while one that moves the operation to a service of another name leaves nothing to match, and the diff reports the move as `operation-removed` plus `operation-added` across the two services, or `service-removed` plus `service-added` when a service goes or comes with it — breaking, as a moved method is. A webhook belongs to no service, so every edit to its `tags` is a `tagsChanged`.

```typescript
interface SuccessResponse {
  statusCode: number; // A declared 2xx or 3xx code
  type: TypeRef; // The body type; always `unknown` for a 3xx entry
  headers?: ResponseHeader[]; // Only when the spec declares at least one
  contentTypes?: string[]; // Media types under `content`, in document order; only when at least one
  contents?: ResponseContent[]; // One per contentTypes entry, same order; only when contentTypes is
  description?: string; // The response's description; only when it has non-whitespace content
}

interface ResponseContent {
  contentType: string; // As written in the spec, e.g. "application/vnd.api+json", "text/html; charset=utf-8"
  type: TypeRef;
}

interface ResponseHeader {
  name: string; // As written in the spec, e.g. "Content-Disposition"
  type: TypeRef;
  required: boolean;
  description?: string;
  deprecated?: boolean;
  externalDocs?: ExternalDocs; // The header schema's (`schema`, or the single `content` entry's), when usable
}

interface Parameter {
  name: string;
  type: TypeRef;
  required: boolean;
  description?: string;
  deprecated?: boolean;
  externalDocs?: ExternalDocs; // The schema's, else the `$ref` target's, when usable
  default?: unknown;
  example?: unknown; // The document's `example`, else `examples[0]`
  examples?: unknown[]; // Every example value, in document order; only when non-empty
  style?: "form" | "simple" | "label" | "matrix";
  explode?: boolean;
  constraints?: Constraints; // Validation keywords; see Constraints below
}
```

`Parameter.description` is the first non-empty `description` found on, in order, the parameter itself, its inline `schema`, and the `$ref`'d component schema. An empty string at any level counts as absent, and the field is `undefined` (never `""`) when nothing in the chain is documented. `deprecated` and `example` fall through the same three levels in the same order, each by its own rule: `deprecated` takes the first truthy level, `example` the first level that gives a value (an explicit `null` is kept; see Parameter Examples below). `default` does not: it is read from the inline `schema`, else the `$ref`'d component schema, with `??`, so a `false` or `0` default is kept, and the Parameter Object itself is never consulted since OpenAPI gives it no `default`. `Parameter.externalDocs` follows the same chain from the schema down — the parameter's `schema` (a sibling of a `$ref` included), then the component schema its `$ref` points at — an unusable entry at one level falling through to the next; a Parameter Object declares no `externalDocs` of its own.

`ResponseHeader.externalDocs` is the header schema's `externalDocs` — the Header Object's `schema`, or the schema of its single `content` entry, after a `$ref` into `components/headers` is resolved — when it declares a usable one. A header reads only its own schema, as its `description` and `deprecated` read only the Header Object: a `$ref` sibling's link is the header's, and a bare `$ref` gives none (the referenced model carries its own).

A parameter's `constraints` come from its own schema. When that schema is a `$ref`, the target's keywords are merged underneath the parameter's own — `{ $ref: Limit, minimum: 5 }` against `Limit: { type: integer, minimum: 1, maximum: 100 }` gives `{ minimum: 5, maximum: 100 }` — the per-value way `default` and `example` fall back, so a parameter can be read on its own without chasing the target (a primitive component becomes a fieldless model; an array component becomes no model). The key is absent when neither declares any.

### Parameter Examples

`example` and `examples` are read from three levels in order: the parameter itself, then its inline `schema`, then the component schema its `$ref` points at. A parameter-level `examples` is an OpenAPI map of Example Objects, so each entry's `value` is taken in document order; a `$ref` entry is resolved against `components.examples` (a dangling ref is skipped with a warning), and an `externalValue` entry is skipped. A schema-level `examples` is the JSON Schema list and is taken as-is.

Each value walks the levels on its own. `examples` is the first level's non-empty list. `example` comes from the first level that has either an `example` or a list, preferring that level's own `example` over its first list entry, so a schema-level `example` can never mask the parameter's own `examples` map. A level with neither falls through; an explicit `null` is a value and is kept. Emitters that read only `example` therefore still see a value for an OAS 3.1 document that uses `examples` alone.

### Idempotency Key

The `injectIdempotencyKey` flag is spec-driven: it is `true` only when the operation explicitly declares an `Idempotency-Key` header parameter in the OpenAPI spec. This means APIs that don't use idempotency keys (e.g., GitHub) get `false`, while APIs that do (e.g., Stripe, billing APIs) already declare the header in their spec and get `true`.

### Request Body Encoding

`requestBody` is read from one entry of the Request Body Object's `content` map (after a `$ref` into `components/requestBodies` is resolved), and `requestBodyEncoding` tells emitters how to serialize it:

| Value             | Media types                                |
| ----------------- | ------------------------------------------ |
| `json`            | `application/json`, any `+json` media type |
| `form-data`       | `multipart/form-data`                      |
| `form-urlencoded` | `application/x-www-form-urlencoded`        |
| `binary`          | `application/octet-stream`                 |
| `text`            | `text/plain`                               |

Media types are matched by essence — `type/subtype` with parameters stripped and case folded, as response media types are (see Multiple Success Responses below) — so `application/json; charset=utf-8`, `APPLICATION/JSON` and `multipart/form-data; boundary=x` are read as their bare types, and `application/vnd.api+json` or `application/merge-patch+json` as JSON. The entries are tried in a fixed order: `application/json`, then a `+json` media type, then `multipart/form-data`, then `application/x-www-form-urlencoded`, each only when it declares a schema (an `application/json` entry without one yields to a later media type that has one); then `application/octet-stream`, then `text/plain`, with or without a schema — a schema-less binary body is a `string` with `format: "binary"`, a schema-less text body a `string`, and one with a schema is typed from it. Within a tier the first matching key in document order wins. `requestBodyEncoding` is set exactly when `requestBody` is, and so is `requestBodyContentType`: the essence of the media type the body was read from (`application/merge-patch+json`; `application/json` for `application/json; charset=utf-8`; `multipart/form-data` for `multipart/form-data; boundary=x`), which is what an emitter sends as the request's `Content-Type` — `requestBodyEncoding` says how to serialize the body, `requestBodyContentType` how to label it, so a server that requires its declared media type accepts the request; parameters such as a multipart boundary are the emitter's to produce. A body that declares media types but none the parser reads — `application/xml`, `text/csv`, or only an `application/json` entry without a schema — yields no `requestBody`, `requestBodyEncoding` or `requestBodyContentType`; it is carried in `requestBodyContents` alone (see Request Body Content Types below), and the parser warns once per operation (and once per webhook, whose payload goes through the same pick) rather than dropping it silently. The `x-mutually-exclusive-body-groups` extension resolves its members from the same pick, as do the body-owned query parameters (`bodyOwnedQueryParams`).

A body that is itself an inline enum, or an array of one, mints no model: it is promoted to `spec.enums` under the `<Op>Request` name it is typed by (`SetMoodRequest`), whichever media type it was read from, with the per-value documentation and link the schema declares (see Enum below). A name an enum of other members already owns — a component's — is numbered (`SetMoodRequest2`), and a name a model owns is never taken; identical members share the existing enum. An enum nested in the body's model (`SetMoodRequest.mood`) is promoted with every other model's field enums (`SetMoodRequestMood`).

### Request Body Required

`requestBodyRequired` carries the Request Body Object's `required` flag, so an emitter can make the body argument mandatory or optional to match the document. It is read after a `$ref` into `components/requestBodies` is resolved, so a referenced body's flag counts. OpenAPI defaults the flag to `false`, so a body the document does not mark required is `false` here — an explicit `required: false` and an omitted flag are the same thing, and only a literal `true` makes a body required. The field is present exactly when `requestBody` is, whatever the encoding or the body's shape (an inline object, a bare `$ref`, a `oneOf`, a schema-less binary or text body); an operation without a body, or whose declared body yields no `requestBody`, has no entry.

The differ reports a flip as `requestBodyRequiredChanged` on an `operation-modified` change: optional → required is breaking (callers must now send a body), required → optional is additive. A body appearing or disappearing is reported as `requestBodyChanged` alone. A body changing type also sets `requestBodyChanged`, and if its required flag flips in the same change, both flags are set. A body change is breaking, except when a body appears with `requestBodyRequired` not `true`: an optional body only gives callers an argument they may leave out, so it is additive, the same as `param-added` for an optional parameter. A body appearing as required, a body disappearing and a changed body type stay breaking, and as with every other flag, one breaking flag makes the whole `operation-modified` change breaking (an optional body added alongside a required parameter is breaking). While both specs declare a body, the media types it may be sent as (`requestBodyContentTypes`) are compared by essence as a response entry's are and reported as `requestBodyContentTypesChanged` with `requestBodyContentTypeChange` beside it: a media type callers could send that is gone, or a secondary media type whose body changed type, is breaking; one they can newly send is additive (see `oagen diff` in the CLI reference). A body changing encoding — `requestBodyEncoding`, the wire format it is serialized as (see Request Body Encoding above) — while both specs declare one sets `requestBodyEncodingChanged`, with `oldRequestBodyEncoding`/`newRequestBodyEncoding` beside it, and is breaking in either direction: an SDK built for the old document keeps serializing and labelling the body as that document said. A body moving from `application/json` to `application/x-www-form-urlencoded` sets both flags — the JSON media type is removed and the form one added — while a media type changing essence within one encoding (`application/json` → `application/vnd.api+json`) sets `requestBodyContentTypesChanged` alone. A body that appears or disappears takes its encoding with it and is `requestBodyChanged` alone; one that changes type and encoding at once sets `requestBodyChanged` and `requestBodyEncodingChanged`. A webhook payload's encoding is compared through the same function (see Webhook below).

### Request Body Content Types

A request body that offers more than one media type (`application/json` and `text/csv` for a widget replaced from a record or from a spreadsheet row; `application/json` and `multipart/form-data` for an upload) keeps every media type it declares, as a response does (see Response Content Types below). `requestBodyContentTypes: string[]` holds the keys of the body's `content` map, in document order and exactly as written — parameters (`application/json; charset=utf-8`, `multipart/form-data; boundary=x`), vendor suffixes and case included — and `requestBodyContents: RequestBodyContent[]` one entry per media type in the same order, with the type that media type resolves to. Both are present only when the body declares at least one media type, whether or not one of them is read as `requestBody`; an operation without a body, or whose body has an empty `content` map, has neither. A key is never normalised or merged: `application/json` and `application/json; charset=utf-8` declared side by side are two entries.

`requestBody` is unchanged: it is still the type of the media type the fixed-order pick chooses (see Request Body Encoding above), the `requestBodyContents` entry for that media type carries the very same `TypeRef`, so the two can never disagree, and `requestBodyContentType` is that media type's essence. Every other entry is typed the way `requestBody` would be if it were the only one declared: from its schema when it has one — a `$ref` stays a reference to the component, an inline object is materialized as a model (below) — else `string` with `format: "binary"` for `application/octet-stream`, `string` for `text/plain`, and `unknown` for any other media type without a schema, a JSON or form media type included, since the pick reads those only with a schema. In the widget example `requestBody` is `ReplaceWidgetRequest` (the JSON wins the fixed order) while `requestBodyContents` reads `[{ application/json → ReplaceWidgetRequest }, { text/csv → string }]`. A body none of whose media types is read (`application/xml` alone) has `requestBodyContents` but no `requestBody`, and the parser warns once, as described under Request Body Encoding.

An inline object declared only for a secondary media type is materialized as a model named from the primary body's name without its `Request` suffix, the media type and `Request` — `ReplaceWidgetTextCsvRequest` beside `ReplaceWidgetRequest`; for an operation without an `operationId`, the path-derived prefix in place of the stem — with nested objects, array items and union variants named under it as `schemaToTypeRef` names them. The media type's fragment is taken from its essence (`mediaTypeNameFragment`): parameters and case are dropped, a wildcard segment reads as `Any`, so two spellings of one media type derive one name — `application/json; charset=utf-8` beside a primary `application/json` is `ReplaceWidgetApplicationJsonRequest`, and a third spelling with a third shape steps to `ReplaceWidgetApplicationJsonRequest2`. The name goes through the same spec-wide shape registry secondary response bodies, headers and fallback bodies use (`materializeInlineSchema`), seeded with every component and primary model before any of them is named and resolved in document order, an operation's secondary request bodies before its response bodies: an identical shape (fields, types, requiredness, limits, defaults and access flags alike) under a taken name shares the model, and a different shape under a taken name — a component's, a primary body's, another operation's — is re-derived with a numeric suffix (`ReplaceWidgetTextCsvRequest2`, `…3`, …); a title-mapped variant whose title is taken falls back to its context-qualified name, and one nested below the top level is renamed under the body's root with every reference rewritten, exactly as a secondary response body's is. An inline enum under a secondary media type, at the top level or inside its models, is promoted to `spec.enums` like a secondary response body's (`ReplaceWidgetApplicationXmlRequestMode`); a clash with a different value set, or with a name a model owns, is renamed with a numeric suffix. The primary body's own `oneOf` handling — a discriminated union of inline objects flattened into one object, a union's variants named from their consts — applies to `requestBody` only; a secondary body is typed as any deferred schema is.

`collectRequestBodyTypes(op)` (exported from `@workos/oagen`) is the request-side twin of `collectResponseBodyTypes`: it yields every request body type an operation declares besides `requestBody` — every `requestBodyContents` entry except the one that shares `requestBody`'s type (`collectAlternateRequestBodyContents`), so every entry when no media type was read — each with a `source` for diagnostics (`requestBodyContents.text/csv`). Every pass that walks an operation's type refs — reachability (`collectReferencedNames`), model assignment (`assignModelsToServices`, `collectRequestBodyModels`), ref rewriting and validation (context `<Service>.<op>.requestBodyContents.<media type>`), the differ's direction index, where such a body is request-facing since the caller constructs it, the compat filter (`specDerivedNames`) and inline-enum collection — calls it beside `collectResponseBodyTypes`, so a body declared only for a secondary media type is emitted like the primary one. A webhook's secondary payloads are reached through `collectWebhookTypeRefs` the same way.

### Multiple Success Responses

`successResponses` holds every 2xx and 3xx response the operation declares, one `SuccessResponse` per status code with its own `type`, `headers` and `description`. A 2xx entry's `type` is its body, read from its `content` map by media type — compared by essence, so parameters and case do not matter (`application/json; charset=utf-8`, `TEXT/PLAIN`) while the keys themselves stay as written — in this order: the JSON schema when one is declared (`application/json`, else a `+json` media type such as `application/problem+json`); else `string` with `format: "binary"` when the map has `application/octet-stream` or `application/pdf`; else `string` when it has `text/plain`, `text/html`, `text/xml` or `application/xml` (a schema written on one of those four is not read); else the schema of the first media type that declares one. It is `unknown` when the response declares no content or none of those rules gives a type: a schema-less `text/csv` body is `unknown`, not `string`, while a `text/csv` body with a schema is typed from that schema. A 3xx entry's `type` is always `unknown`; the entry is kept so an emitter can recognize a redirect endpoint rather than try to deserialize a body. The list is set only when more than one such response is declared, counting 2xx and 3xx together: `200` + `201`, `200` + `302` and `301` + `302` all set it, while a lone `200` (or a lone `302`) leaves it `undefined`. Every 2xx body's inline models are named under the operation's one `<Op>Response` context, the primary's first (the lowest status code whose body has a type): a later status code's model whose name the primary's already holds resolves to the primary's definition and is dropped, with a warning when its fields differ, and the models only that dropped copy referenced go with it — `{ owner: { id } }` as the 201 body beside a 200 `{ id }` leaves no `CreatePetResponseOwner` behind — so no model is left that nothing references. Of a later status code's models, those its entry's `type` still reaches are kept (a nested model the primary holds under the same name is read through the primary's); the primary's are all kept, its paging companions included. 4xx and 5xx responses go to `errors`; `default` and the ranges `1XX`–`5XX` go to `defaultResponse` and `rangeResponses` (see Default and Range Responses below); an explicit 1xx code is not carried. A key is a status code only when it is exactly three digits in 100–599; a key that merely starts with digits (`6XX`, `4XXX`, `20X`, `600`, `200 `) is neither a status code nor a range and is ignored with a warning (see Default and Range Responses below).

`response` always points at the primary response: the lowest declared status code whose type is not `unknown` — the lowest 2xx with a typed body, so a `200` whose body the media-type rules leave `unknown` (a schema-less `text/csv`) yields to a `201` typed from a schema, and `response` and `responseDescription` then come from the `201` — falling back to the lowest declared code (an untyped 2xx, or a 3xx when the operation declares no 2xx). `responseHeaders` and `responseDescription` come from that same entry, whether or not `successResponses` is set. An operation declaring no 2xx or 3xx response at all (only `default` or `2XX`, only a `404`, an empty `responses` map, or no `responses` key) has `response` set to `{ kind: "primitive", type: "unknown" }` — the type of a body the document does not describe — with no `responseDescription` or `responseHeaders`: a `2XX` range or `default` body is never promoted into `response` (see Default and Range Responses below). An emitter that handles status codes differently (200 vs 204, or a 302 beside a 200) reads `successResponses`; one that only needs the return type reads `response`.

A 2xx body that is itself an inline enum, or an array of one, mints no model: it is promoted to `spec.enums` under the `<Op>Response` name the body is typed by (`GetPetKindResponse`), with the per-value documentation and link the schema declares (see Enum below). When `successResponses` is set, each entry's body is promoted on its own under its status code: every entry derives the same `<Op>Response` name, so identical members share one enum, and a body with other members — or the same values deprecating a different one — is qualified with its status code (`CheckPetKindResponse202`), then numbered. A body whose name an enum of other members already owns — a component's — is qualified the same way when `successResponses` is set (`CheckPetKindResponse200`, which a later entry with the same members shares) and numbered otherwise (`GetPetKindResponse2`); a name a model owns is never taken. The request body's enum is promoted the same way under `<Op>Request` (see Request Body Encoding above).

```yaml
responses:
  "200":
    description: The pet
    content:
      application/json:
        schema: { type: string }
  "302":
    description: Moved
```

```typescript
op.response = { kind: "primitive", type: "string" };
op.responseDescription = "The pet";
op.successResponses = [
  {
    statusCode: 200,
    type: { kind: "primitive", type: "string" },
    description: "The pet",
  },
  {
    statusCode: 302,
    type: { kind: "primitive", type: "unknown" },
    description: "Moved",
  },
];
```

### Response Descriptions

A response's `description` — often the clearest statement of what an operation gives back ("The pet, with its owner.", "Not found") — is kept with the status code it belongs to as `description` on each `SuccessResponse` and `ErrorResponse`. Because `successResponses` is only set when more than one 2xx or 3xx response is declared, the primary response's description (the one `response` is the body of) is also exposed directly as `Operation.responseDescription`, where an emitter can print it as a `@returns` tag. All three fields follow the rule `Operation.summary` uses: present only when the document declares a description with non-whitespace content, kept verbatim when it does, and omitted otherwise — a description is never borrowed from another status code. A `$ref` into `components/responses` is resolved first, so the component's `description` is read; in an OAS 3.1 document a `description` written next to the `$ref` overrides it (outermost first along a chain), while in an OAS 3.0 document, where properties beside a `$ref` are ignored, the component's own is kept. A ref nothing resolves is read as written, so only its sibling `description` is seen. When a doc URL base is configured, relative links are expanded in response descriptions exactly as in `description`. The differ does not report a changed response description, the same as a changed operation description.

### Response Headers

Headers a response declares (`Content-Disposition` on a download, `Location` after a create, `ETag`, rate-limit headers) are kept with the status code they belong to as `headers: ResponseHeader[]` on each `SuccessResponse` and `ErrorResponse`. Because `successResponses` is only set when more than one 2xx or 3xx response is declared, the primary response's headers are also exposed directly as `Operation.responseHeaders`.

Each header is typed like a parameter via its `schema` (or the first media type of its `content` map); a header with neither is a `string`. `$ref`s into `components/headers` are resolved, and a `description` written next to the `$ref` overrides the component's (OpenAPI 3.1); a ref that cannot be resolved is warned about and dropped rather than failing the parse. A header named `Content-Type` is ignored, as OpenAPI requires. All three fields are present only when at least one header survives, so operations without headers keep their shape.

An object-shaped header (directly, inside an array, or as a oneOf variant) is materialized as an inline model named from the service and header name (`Documents` + `X-Meta` → `DocumentsXMeta`), nested objects included (`DocumentsXMetaOrigin`). Because that name can already belong to a differently shaped component schema, to the same header on another status code, or to the same header on another operation of the service, the parser keeps a spec-wide registry of model shapes, filled once every operation has been read: component models first, then every inline model the operations mint for request bodies and primary response bodies (nested objects and union variants included) and the shared envelope companions, then each header, secondary body and parameter in document order (path order; within an operation its responses first — ascending status code, headers before bodies — then its parameters). The registry also holds every enum name — the component enums' and the name every inline enum a model field, a parameter or a body mints is lifted under (`PetsKind`) — which no model may take, so a deferred model named like an enum steps as it would beside a component of another shape. The first owner of a name keeps it, and a later header with a different shape is re-derived under the first free candidate — bare name; then each name an earlier `X-Meta` header of the service settled on, in the order they were resolved and with the renames made under it replayed, so a header identical to one that had to step past a taken bare name shares its model under that name, nested models included (when a title-mapped variant of the 200 body owns `DocumentsXMeta`, the 200's header settles on `DocumentsXMeta200` and the identical 429 header shares it rather than minting `DocumentsXMeta429`) while a different shape steps past it; then the status code (`DocumentsXMeta429`) when the clash is inside the same operation, or the operation (`DocumentsCreateDocumentXMeta`) when it is with a component, a primary body or another operation; then the other of those two; then both (`DocumentsCreateDocumentXMeta429`); then a numeric suffix (`DocumentsXMeta2`, `DocumentsXMeta3`, …). A union variant named from its title (`Circle`) does not change with the candidate, so every taken name is also reserved for the extractor, which gives such a variant its context-qualified name instead (`CircleDocumentsXMeta`); a titled variant nested below the top level, which no reservation reaches, is renamed under the header's root (`DocumentsXMetaCircle`) with every reference rewritten (`materializeInlineSchema`, see Default and Range Responses below), so naming always terminates. A header whose shape matches the name's owner shares it and materializes nothing new, so a header matching a component schema simply references that schema; the shape covers every field's type, requiredness, limits, default and access flags and the model's own limits, so two headers that differ only in a `minLength` keep separate models. Inline header enums follow the same idea with their own, status-code-based rule, applied inside a header's models too, so a nested enum whose name a component enum already owns with other values is renamed rather than silently given the component's values.

A parameter in any location — path, query, header or cookie, a query parameter the body owns included — whose inline schema mints a model (an object, as a `style: deepObject` query parameter is; an array or map of objects; a union with an inline object variant; a nullable wrapper around one; at any depth) is materialized through the same registry, named from the service and parameter name as `schemaToTypeRef` referenced it (`Pets` + `filter` → `PetsFilter`, nested objects `PetsFilterOwner`), with the parameter's location where a header has its status code: the bare name; then the location (`PetsQueryFilter`) when the clash is inside the same operation — one name in two locations, or a response header of the same name, which the operation typed first and which keeps its name (`PetsXMeta` for the header, `PetsHeaderXMeta` for the header parameter); or the operation (`PetsListPetsFilter`) when it is with a component model, a component enum, an enum another parameter or a field lifts (`PetsKind` on `listPets`, so `kind` on `searchPets` is `PetsSearchPetsKind`), a primary body or another operation; then the other of those two; then both (`PetsListPetsQueryFilter`); then a numeric suffix (`PetsFilter2`, …). A parameter whose shape matches the name's owner shares it, so the same `filter` on two operations of one service is one `PetsFilter`. A parameter that mints no model — a primitive, a `$ref`, an inline enum, an array of either — keeps the type `schemaToTypeRef` gave it and is not registered; an inline parameter enum is still lifted under its service-qualified name (`PetsKind`). Webhook parameters are materialized under the webhook's stem instead (see Webhook).

`collectResponseHeaders(op)` (exported from `@workos/oagen`) yields every header list once — the primary list is the same array as its `successResponses` entry — and is what reachability, model assignment, ref rewriting/validation, the differ, and the compat filter use, so a model or enum reached only through a header is emitted like any other.

### Response Content Types

A response that offers more than one media type (`text/html` and `application/pdf` for a card that renders as a page or a printout; `application/json` and `application/vnd.api+json`; `application/json` and `*/*`) keeps every media type it declares. Each `SuccessResponse` and `ErrorResponse` carries `contentTypes: string[]` — the keys of its `content` map, in document order and exactly as written, parameters (`application/json; charset=utf-8`), vendor suffixes and wildcards included, so an emitter can offer them verbatim in an `Accept` header — and `contents: ResponseContent[]`, one entry per media type in the same order, with the type that media type's schema resolves to. Both are present only when the response declares at least one media type; a response without `content` (a 204, a redirect without a body) or with an empty `content` map has neither. As with headers, the primary success response's two lists are also exposed on the operation as `responseContentTypes` and `responseContents` (the same arrays), because `successResponses` only exists when there is more than one 2xx or 3xx response.

`Operation.response` is unchanged: it is still the type of the media type the parser's fixed-order pick chooses (the JSON schema — `application/json`, else a `+json` media type; else `application/octet-stream` or `application/pdf` as binary; else `text/plain`, `text/html`, `text/xml` or `application/xml` as a string; else the schema of the first media type that declares one — each matched by essence, see Multiple Success Responses above). The `contents` entry for that media type carries the very same `TypeRef` as `response` (and as `type` on the `SuccessResponse`), so the two can never disagree. Every other media type is typed the way `response` would be if it were the only one declared — binary for `application/octet-stream` and `application/pdf`, a string for the text and XML types whatever their schema says, the schema's type for anything else, and `unknown` for a media type with no schema. In the card example `response` is binary (the PDF wins the fixed order) while `contents` reads `[{ text/html → string }, { application/pdf → binary }]`. A 3xx entry's `type` is not read from any media type, so each of its entries is typed on its own. An error entry's `type` is read from its JSON body — `application/json`, else the first `+json` media type (`application/problem+json`), matched by essence as for a fallback response — and is otherwise untouched; its `contents` entry for that media type shares it, and the others are typed as above. Because an error's `type` is its JSON body by definition, an error carries the two lists only when they say something `type` does not — it declares another media type (`text/html` beside `application/json`), a JSON media type other than plain `application/json` (`application/problem+json` alone, or `application/json; charset=utf-8`), or a JSON body with no schema that `type` could not be read from. An error that declares only `application/json` with a schema, the overwhelmingly common case, keeps exactly the shape it had.

An inline object declared only for a secondary media type is materialized as a model named from the operation's response stem, the media type and the entry's role — `RenderPetCardTextHtmlResponse`, `RenderPetCardApplicationProblemJsonError` — with nested objects, array items and union variants named under it as `schemaToTypeRef` names them. Which keyword types an ambiguous schema — `allOf` before `oneOf`/`anyOf`, before `items`, before `properties`, before a bare map — is decided once by `classifyInlineSchema`, which `schemaToTypeRef` and every inline-model extractor dispatch on, so the models materialized are exactly the ones the type references. The media type's PascalCase form is taken from its essence — parameters stripped, case folded (`mediaTypeNameFragment` in `src/utils/media-type.ts`) — so a key that only respells itself between two spec versions keeps its model name (`application/yaml` and `application/yaml; charset=utf-8` both give `ApplicationYaml` when each is the only YAML key), which is what lets `oagen diff` see an unchanged body; a wildcard segment reads as `Any` (`ApplicationAny`). Two keys of one essence declared side by side in one response are told apart by their parameters, lower-cased and cased after the essence (`application/yaml` → `ApplicationYaml`, `application/yaml; charset=utf-8` → `ApplicationYamlCharsetUtf8`), so each spelling's name does not depend on the keys' order and reordering them is no change; two such keys that differ only in case (`application/yaml`, `Application/YAML`) take the same name and go through the registry described next, in document order. The name goes through the same spec-wide shape registry headers and fallback bodies use (`materializeInlineSchema`, see below), seeded with every component (and every model a component's field mints) and primary model before any of them is named, and resolved in document order. A component's name is shared by every shape the component admits — the same fields and types, the component no stricter on requiredness or nullability, everything else identical; the one rule by which an inline model folds onto a component anywhere (see Models) — and an operation's model by an identical shape only (fields, types, requiredness, limits, defaults and access flags alike). So an identical shape on another status code shares the model under whichever name that status code's body settled on — the bare name, or the `…Response200` it took when a component, a primary body or another operation owned the bare name with a shape it does not share — because each site tries, after the bare name, the names the earlier sites of the same bare name settled on, before its own, replaying the renames made under each (a nested titled variant renamed under the body's root, `…ResponseCircle`, is built under that name again, so it is shared too); the sites of one bare name are the bodies whose keys derive it — the same key on two status codes, a key respelled without parameters another key beside it shares (`application/yaml; charset=utf-8` alone on the 200, `application/yaml` on the 201), two keys of one response that differ only in case — while two spellings side by side told apart by their parameters derive two names and never share; a shape the owner of a taken name does not share — a component that does not admit it, a differing primary body, another operation's or an earlier status code's model — is re-derived with its own status code (`…Response201`), then a numeric suffix (`…Response2`, `…Response3`, …), and a status code after it with that shape shares it in turn (`…Response202` for a 202 and the identical 203); a title-mapped variant whose title is taken falls back to its context-qualified name (`CircleRenderPetCardApplicationVndShapeJsonResponse`), and one nested below the top level, which no reservation reaches, is renamed under the body's root (`RenderPetCardApplicationVndShapeJsonResponseCircle`) with every reference rewritten, exactly as a header's or a fallback body's is. An inline enum under a secondary media type, at the top level or inside its models, is promoted to `spec.enums` like a header's; a clash with a different value set, or with a name a model owns, is renamed with a numeric suffix.

`collectResponseBodyTypes(op)` (exported from `@workos/oagen`) yields every response body type an operation declares besides `response`, each with a `source` for diagnostics (`contents.text/html`): today the bodies of its secondary media types — every content entry except the one that shares the response's own `type`, which `response`, `successResponses[].type` and `errors[].type` already cover, each list once — then the fallback bodies of its `default` and range responses (`defaultResponse`, `rangeResponses.4XX`). It is the one place to extend: reachability, model assignment, ref rewriting/validation, the differ, the compat filter and enum collection all call it beside `collectResponseHeaders`, so a body declared only for a secondary media type is emitted like the primary one.

### Default and Range Responses

OpenAPI lets a Responses Object carry two kinds of key besides explicit status codes: `default`, which applies to every status the operation does not list, and the ranges `1XX`–`5XX`, each of which applies to every status in its hundred that is not listed explicitly. Neither has a status code, and `ErrorResponse.statusCode` / `SuccessResponse.statusCode` are numbers that emitters compare and format as such, so they live in two additive fields instead of being folded into `errors` or `successResponses`:

| Document key     | IR                                                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------------------------------- |
| `default`        | `Operation.defaultResponse: { type?, contentTypes?, contents?, headers?, description? }`                          |
| `4XX` (or `4xx`) | an entry of `Operation.rangeResponses: { range: '4XX', type?, contentTypes?, contents?, headers?, description? }` |

To resolve what an operation returns for a status, an emitter follows OpenAPI's own precedence: the explicit entry (`successResponses`/`errors`), then the range the status falls in (`rangeResponses`), then `defaultResponse`. In practice `defaultResponse.type` is the API's error shape, so an emitter can type the errors it does not list individually. Both fields are absent — not empty — on an operation that declares neither.

What the parser deliberately does not do:

- **No promotion.** `response` is still the primary pick described under Multiple Success Responses (the lowest explicit 2xx or 3xx with a typed body, else the lowest declared); an operation whose only success is `default` or `2XX` has `response` set to `{ kind: 'primitive', type: 'unknown' }`, the type of a body the document does not describe. What to use instead: an emitter resolves any status as the explicit entry, then the matching `rangeResponses` entry, then `defaultResponse` — so when no explicit 2xx exists, the success body is the `2XX` range's `type`, then `defaultResponse.type`. `errors` is likewise untouched.
- **No synthetic codes.** A `4XX` is never recorded as a `400`, which would make an emitter claim a code the spec does not.

A fallback response written as a Reference Object (`default: { $ref: '#/components/responses/Problem' }`) is resolved first — chains are followed, JSON Pointer escapes honored, and a `description` written beside the `$ref` wins over the component's in an OAS 3.1 document and is ignored in a 3.0 one; a ref nothing under `components/responses` answers is warned about and the response read as written, with no body or headers — the same rules as for an explicit status code (see "Shared through `components/responses`" under Inline model naming). The body is then read from `application/json`, else the first `+json` media type (`application/problem+json`), matched by essence; other media types leave `type` unset, as they do for `errors`. Every media type the response declares is kept in `contentTypes`/`contents` exactly as on a `SuccessResponse` (see Response Content Types above): present whenever there is at least one, the entry for the media type `type` was read from sharing that very `TypeRef` — so a reader can tell a `default` typed from `application/problem+json` apart from one typed from `application/json` — and every other entry typed on its own, an inline object under it materialized as `<Op>Default<MediaType>Response` (`ListPetsDefaultApplicationYamlResponse`) or `<Op>ClientError<MediaType>Response`. The differ reports a media type such a response gains, loses or retypes under `responseContentTypeChanges` with `fallback` set (`'default'`, `'4XX'`) in place of `statusCode`, matching the two specs' media types by essence — case folded, parameters stripped — as the parser types them, so `application/problem+json; charset=utf-8` is `application/problem+json` to it (see `oagen diff` in the CLI reference).

The body is typed as if it were a field named `<Op>DefaultResponse` or, for a range, `<Op>` + the range's word + `Response` — `Informational`, `Success`, `Redirect`, `ClientError`, `ServerError` (`ListPetsClientErrorResponse`), because `4XX` does not survive PascalCasing — of a parent with no name, through the same extractor every field goes through. So a `$ref` is the referenced model, and every shape a field can take is materialized under that name by the field rules: an inline object (`ListPetsDefaultResponse`), a nullable one, nested objects (`…Detail`), array items and map values (they take the body's name, as a field's items take the field's), `oneOf`/`anyOf` variants (`…`, `…WithReason`), an `allOf` merge. The ref and the models agree by construction, so nothing dangles. The body is named once every operation has been read, in document order with the header and secondary-body schemas (`resolveDeferredInlineTypes`), and its names are checked against the spec-wide model registry (components and the inline models their fields mint — a nested object, a map's values — every operation's request body and primary response models, envelope companions, and every header, secondary-body and fallback model named so far) by the same `materializeInlineSchema` helper header and secondary-body models use: a body whose shape matches the name's owner shares it and materializes nothing new (a header or secondary body also tries, between its bare name and its own qualifiers, the names the earlier sites of the same bare name settled on — see Response Headers and Response Content Types above — while a fallback body's bare name carries the response's label and an error body's its status code, so within an operation neither has such a sibling), and a clash is cleared by the cheapest move that can still change something — a `oneOf`/`anyOf` variant named from its own `title` or const is reserved so variant naming steps around it (`CircleListPetsDefaultResponse`, as beside a sibling's model), and a name derived from the stem (the root, nested objects, array items) moves the whole body to the next free stem (`ListPetsDefaultResponse2`, `…3`), nested models and ref together. The clashing set is compared between attempts, so when a stem advance changes nothing the loop stops (no input can make it retry forever; a hard cap backs the test) and the clashing names themselves are renamed under the root (`ListPetsDefaultResponseCircle`), then numbered, with every reference rewritten to match — the case of a titled variant nested below the top level, where no reservation reaches. Sameness is decided on the final shapes, after every rename: renaming a child changes its parent's shape, so a parent that matched a registered model (a component `ListPetsDefaultResponse` whose `shape` points at the component's own `Circle`) and no longer does moves to the next free stem with its children (`ListPetsDefaultResponse2`, `ListPetsDefaultResponse2Circle`; a header's next qualified candidate) rather than being dropped as already defined, which would leave the body resolving to the component and its old child. The move is decided per model, by shape: a child whose name an identical definition already owns (a component, an earlier operation's model) stays shared under that name and the moved parent keeps referencing it, exactly as it is shared when nothing moves; only the root and the children that need distinct names move. A schema that both inlines such a clashing `Circle` and `$ref`s component `Circle` fails the parse with a message naming both, since the rewrite could not tell the two references apart. So a component, or another operation's response or request body, that happens to carry a fallback's name is never overwritten by inline-model merging. A body that is itself an inline enum, or an array of one, is typed like a parameter and promoted to `spec.enums` under the same name, numbered on a clash with an enum of other values or with a name a model owns; enums nested in a fallback's models are collected with every other model's, and a field enum whose name an enum of other values already owns is numbered the same way (`ListPetsDefaultResponseStatus2`) rather than left pointing at those values. List-envelope and pagination detection are skipped, since a fallback body is not what the SDK method returns.

Headers declared on these responses are kept as `headers` and qualified by the response's label where a status code would qualify an explicit response's (`PetsXMetaDefault`, `PetsXPolicyClientError`); `collectResponseHeaders(op)` yields them after the explicit lists. `collectFallbackResponseTypes(op)` (exported from `@workos/oagen`) yields the `default` body then each range body; it feeds `collectResponseBodyTypes(op)` (see Response Content Types above), which every pass that walks an operation's type refs — reachability, model assignment, ref rewriting and validation, direction, the compat filter, enum collection — goes through. The differ reports a `default` or range response added as additive and one removed or retyped as breaking (`OperationModified.fallbackResponsesChanged`).

Keys the specification does not define are not dropped silently. The whole key decides what it names, in one shared classifier (`classifyResponseKey`) every reader of a Responses Object goes through: a status code is exactly three digits in 100–599, a range is `1XX`–`5XX` in either case, `default` is itself, and an `x-` extension key is skipped. Any other key is warned about (`Ignoring response key "…"`) and ignored, with no model minted for its body — `error` and `Default`, and just as much a key that only starts with digits: `6XX`, `4XXX` and `20X` are neither a range nor a code, `600` and `099` are outside 100–599, and `200 ` (with a trailing space) is not a code either; none is read from its numeric prefix. A duplicate range (`4XX` beside `4xx`) keeps the first and warns. A webhook's responses apply the same classifier (see Webhooks below).

## Webhook

Source: `src/parser/webhooks.ts`

A webhook is a request the API sends to its users. OpenAPI 3.1 describes them under a top-level `webhooks` map whose keys name path items; the parser reads that map into `ApiSpec.webhooks`, one `Webhook` per HTTP method of each entry, in document order. A webhook is not an SDK method: it has no path, belongs to no `Service`, gets no resolved operation name, and is untouched by operation hints and mount rules. What an emitter does with it is generate a payload type, or a typed handler, per event.

```typescript
interface Webhook {
  name: string; // The key under `webhooks`, verbatim: "petAdopted", "user.created"
  operationId?: string; // When the document declares one
  httpMethod: HttpMethod;
  summary?: string; // As on Operation: the operation's own, else the path item's
  description?: string; // As on Operation: summary + "\n\n" + description when both have content
  externalDocs?: ExternalDocs; // The operation's own, when usable, as on Operation
  deprecated?: boolean; // Present, and true, only when deprecated
  tags?: string[]; // As on Operation: document order, unusable entries dropped, only when at least one remains
  headerParams: Parameter[]; // Signatures, event types, delivery ids
  queryParams: Parameter[];
  cookieParams?: Parameter[]; // Only when any exist
  requestBody?: TypeRef; // The payload the receiver is handed
  requestBodyEncoding?:
    "json" | "form-data" | "form-urlencoded" | "binary" | "text";
  requestBodyContentType?: string; // The essence of the media type the payload was read from, as on Operation; present exactly when requestBody is
  requestBodyRequired?: boolean; // Present, and true, only when the body is `required`
  requestBodyContentTypes?: string[]; // Media types the payload declares, in document order (only when any exist)
  requestBodyContents?: RequestBodyContent[]; // A type per media type above, same order (only when any exist)
  responses: WebhookResponse[]; // What the sender expects back
  security?: SecurityRequirementSet[]; // Same semantics as Operation.security
}

interface WebhookResponse {
  statusCode: number;
  description?: string;
}
```

`summary`, `description` and `externalDocs` are read as an operation's are: `summary` and `description` from the operation or, for each the operation declares none with content for, from its path item — the entry itself, or the `components/pathItems` item its `$ref` leads to (text written beside the `$ref` is not read, as nothing beside a `$ref` is) — combined into `description` by the operation's rule; `externalDocs` from the operation alone, since a Path Item Object has none. Everything else is read from the receiver's side of the wire. `headerParams`, `queryParams` and `cookieParams` are the values the request carries, typed exactly as an operation's parameters are (`components/parameters` refs resolved, a path-item-level parameter overridden by an operation-level one of the same identity); a parameter with an inline object schema, or an array of them, is materialized as a model under the name the parameter references (`<Stem>XMeta`, `<Stem>Filter`), so no parameter type dangles — and when a name it would mint is already taken by the payload or an earlier parameter of the same webhook (a query parameter named `payload` would mint the body's `<Stem>Payload`, one named `payload_pet` the body's nested `<Stem>PayloadPet`, a header `X-Meta` and a query `x_meta` would both mint `<Stem>XMeta`), the parameter is typed and minted under its location-qualified name instead (`<Stem>QueryPayload`, then `<Stem>QueryPayload2`, …), the first that takes nothing already minted, with its reference following; a `path` parameter has nowhere to go and is dropped with a warning. `requestBody` is the payload, read like an operation's body (`components/requestBodies` refs resolved, the same media-type pick by essence, a schemaless binary or text body typed as a primitive), with `requestBodyEncoding` and `requestBodyContentType` beside it as on an operation; `requestBodyContentTypes` and `requestBodyContents` carry every media type the payload declares, read as `Operation.requestBodyContents` is (see Request Body Content Types), with an inline object under a secondary media type materialized as `<Stem><MediaType>Payload` (`PetAdoptedTextCsvPayload`, the fragment from the media type's essence) and named by the stem rules below, so it takes part in the stem's collision check like `<Stem>Payload` itself. `responses` lists the status codes the sender expects the receiver to return, one entry per status code key (three digits, 100–599, as the shared `classifyResponseKey` decides) in document order with the document's description, following a `components/responses` `$ref` for it (chains included; a description written beside the `$ref` wins; a ref that leads nowhere keeps the code without a description, with a warning); `default`, range keys such as `2XX` and `x-` keys are not carried, a key that is none of those (`error`, `6XX`, `600`) is warned about and ignored exactly as on an operation, and body schemas on these responses are not carried either, since a webhook response is an acknowledgement. `security` mirrors the document the way `Operation.security` does: `undefined` inherits `ApiSpec.security`, `[]` means none.

One `webhooks` key may declare several methods, so `name` alone does not identify a webhook; `name` + `httpMethod` does, and that pair is what `oagen diff` keys its `webhook-added` / `webhook-removed` / `webhook-modified` changes on. A `webhook-modified` change reads from the receiver's side: a payload type, encoding or `requestBodyRequired` change sets `requestBodyChanged` with `details` saying which (type, encoding and required → optional are breaking; optional → required is additive) and, for an encoding change, `oldRequestBodyEncoding`/`newRequestBodyEncoding` beside the flag as an `operation-modified` change carries them, and so does a change to the media types the sender may use (`requestBodyContentTypes`, compared by essence, both sides declaring a payload), with `requestBodyContentTypeChange` beside it listing them (a media type the sender can newly use, or whose body changed type, is breaking — the handler must decode it; one it can no longer use is additive), a change to the status codes the sender accepts sets `responsesChanged` (a code no longer accepted is breaking, since a handler that keeps returning it now fails the delivery; a newly accepted one is additive; descriptions are not compared), and parameters are matched by location and name — a header and a query parameter may share one — with every `ParamChange` carrying its `paramLocation` (added is additive, removed breaking, optional → required additive, required → optional breaking). The webhook's own `deprecated` flipping sets `deprecatedChanged`, with `oldDeprecated`/`newDeprecated` beside it, and a parameter's is a `param-deprecated-changed` entry in `paramChanges`; both are additive in either direction and mirrored into `behaviorChanges` as `webhook` and `webhook-parameter` nodes, exactly as an operation's are (see [Deprecation](#deprecation)). The security the request carries — `webhook.security ?? spec.security` on each side, a webhook that inherits on both sides being left to the document-level `security-changed` change — sets `securityChanged` with `oldSecurity`/`newSecurity` beside it, read from the receiver's side: a credential the sender stops presenting, or an alternative it may now present that the handler never checked for, is breaking; a credential it starts carrying beside the old ones, or an alternative withdrawn, is additive; the change is mirrored into `behaviorChanges` as a `webhook` node (see the security paragraph under [Service & Operation](#service--operation)). The webhook's `tags` differing, in document order, sets `tagsChanged` with `oldTags`/`newTags`, additive always. An entry that is a `$ref` into `components/pathItems` is resolved, chains included (fields written beside the `$ref` are not merged in, since OpenAPI leaves such a conflict undefined); a ref anywhere else, a cycle, or an entry that is not an object is warned about and skipped (a ref the document cannot resolve at all fails the bundle before parsing, as any dangling ref does). A value under `webhooks` that is not an object is ignored with a warning.

**Payload models.** An inline payload schema is materialized the way a component field's would be: the parser types it as the `payload` property of a synthetic object named by the webhook's _stem_, so the reference and the model are named by the same code and always agree. An inline object becomes `<Stem>Payload`, with nested objects qualified under it (`<Stem>PayloadPet`) and inline enums promoted as `<Stem>Payload<Field>`; a `oneOf`/`anyOf` of inline objects stays a union — discriminator intact, because an event handler switches on it — with its variants named as any field-level union's are (`<Stem>Payload`, `<Const><Stem>Payload`, …); a `$ref` stays a reference; a payload that is itself an inline enum is promoted as `<Stem>Payload`. Nothing is flattened. Inline parameter enums are qualified with the stem the way a service name qualifies an operation's (`PetAdoptedXEventType`).

The stem is the `operationId` when the operation declares one — cleaned exactly as an operation's own `…Request` model name is, so `adoptions_created` gives `AdoptionCreatedPayload` — and the PascalCase of the key otherwise (`pet.returned` → `PetReturnedPayload`). When a key's path item declares several methods, a key-derived stem has the method appended (`PetUpdatedPostPayload`, `PetUpdatedPutPayload`); an `operationId` is unique per document and needs no qualifier, with one caveat: two keys that `$ref` the same `components/pathItems` entry resolve to one operation and so carry one `operationId`, which is what that section is for, so they share one stem and one set of models (`SharedPayload`, minted once) while each stays its own `Webhook` with its own IR nodes; without an `operationId` such keys keep their key-derived stems (`APayload`, `BPayload`). An `operationId` that two different operations declare, which no valid document does, is ignored for naming with a warning, and those webhooks take their key-derived stems. A key that PascalCases to nothing, or to something starting with a digit, gets `Webhook` in front (`Webhook2FaEnabledPayload`). Whether a stem collides is decided from the names it actually mints: every webhook is first minted under its plain stem and the model and inline-enum names that produces — payload, nested objects, union variants with their const or title prefixes, parameter models, parameter and field enums — are compared, by exact name, against every model and enum name the rest of the parse has already decided (component models and enums, the operations' inline models, response-header models and envelope companions, the components' own inline field models, and every inline enum any of those reference; webhooks are extracted last for this reason) and against the names every other webhook mints. Two keys that flatten to one stem (`pet_adopted` and `petAdopted`) collide on every name; a `petEvent` union variant pinning `kind: returned` and a webhook keyed `returnedPetEvent` collide on the single name `ReturnedPetEventPayload`; a component `Event` whose `payload` field is a map of inline objects owns `EventPayload`, so a webhook keyed `event` collides; a stem that merely starts with another's does not collide unless a name coincides. A colliding stem takes the first six hex characters of the SHA-1 of its `operationId` when it is named from one and of its key otherwise, before the method qualifier (`PetAdoptedB4A950Payload`), the rule an operationId-less operation's path prefix follows, and is minted again under it; both sides of a webhook-to-webhook collision are hashed, since neither key is more canonical. A key that stops colliding returns to its plain stem, and the outcome depends only on the document, never on its order. A name that does not embed the stem — a title-mapped union variant, context-free by design — cannot be moved by the hash, so a clash on it alone leaves the stem plain and is left to the model merge, which shares the component's name when the component admits the variant's shape and renames the variant under the webhook's stem otherwise (`PetAdoptedComp`), as for operations.

**Downstream.** `collectWebhookTypeRefs(webhook)` (exported from `@workos/oagen`) yields a webhook's parameter and body types, and every pass that walks an operation's type refs walks a webhook's through it: reachability (`collectReferencedNames` with `opts.webhooks`, so a payload model is never pruned as an orphan, in a scoped run as much as a full one — webhooks are not a service, so no scope selects or excludes them), the `…Json` collapse's ref rewriting, model-ref validation (context `webhooks.<name>.<method>.…`), inline-enum promotion (with the value check response-header enums get: a name already taken by a different value set, or by a model, is renamed, `PetAdoptedXSource2`, rather than silently shared), and the differ's direction index, where a payload or parameter model is response-facing — the user reads it and never constructs it, so a newly required payload field is additive. Payload models belong to no service in `assignModelsToServices`: they stay unassigned unless a service also references them or a `modelHints` entry pins them.

`x-webhooks`, the extension some OpenAPI 3.0 documents use for the same thing, is deliberately not read — it has no agreed shape — and a document that carries one gets a warning saying so. The standard `webhooks` key is read on any 3.x document.

An operation's `callbacks` (OpenAPI 3.x) — the requests the API makes back to a URL the caller supplied in its request, each a path item keyed by a runtime expression such as `{$request.body#/callbackUrl}` — are not read, on an operation under `paths` or on one under `webhooks`: the IR has no node for a request tied to the operation that provoked it, so a callback's request body never becomes a model. Every site that reads an operation declaring at least one callback gets one warning — a `paths` operation once, a `webhooks` (key, method) entry once each, so two keys that `$ref` one `components/pathItems` entry are reported under each key — naming the site (the `operationId`, else `METHOD /path`; `webhooks.<key>.<method>` for a webhook's operation) and the callback keys in document order; the operation is otherwise parsed exactly as it would be without them. An empty `callbacks` map, or a value that is not a map, declares no callback and is silent. A `$ref` into `components/callbacks` is reported at the operation that writes it, under the key it is written as; an entry under `components/callbacks` that no operation references is not reported, since nothing reaches it. The path item under a callback has the shape of a `webhooks` entry, so declaring it there gets its payload typed.

## Model & Field

```typescript
interface Model {
  name: string; // PascalCase, e.g., "Organization"
  description?: string;
  externalDocs?: ExternalDocs; // The schema's externalDocs, when usable
  deprecated?: boolean; // The schema's own `deprecated: true`; absent otherwise (see Deprecation below)
  fields: Field[];
  typeParams?: TypeParam[]; // Generic type parameters
  variants?: TypeRef[]; // A named union's members, one per non-null oneOf/anyOf variant (see Named unions)
  compositionKind?: "oneOf" | "anyOf"; // Which keyword produced `variants`; present exactly when `variants` is
  discriminator?: { property: string; mapping: Record<string, string> }; // Dispatch property and value → IR model name
  constraints?: Constraints; // The object schema's own minProperties / maxProperties / dependentRequired
}

interface Field {
  name: string; // snake_case from the spec
  type: TypeRef;
  required: boolean;
  description?: string;
  externalDocs?: ExternalDocs; // The field schema's own, a $ref sibling included; a bare $ref yields none (see ExternalDocs)
  readOnly?: boolean;
  writeOnly?: boolean;
  deprecated?: boolean;
  default?: unknown;
  example?: unknown; // The schema's `example`, else `examples[0]`
  examples?: unknown[]; // The JSON Schema `examples` list; only when non-empty
  constraints?: Constraints; // Validation keywords on the field's schema, siblings of a $ref included; a bare $ref yields none
}
```

### Named unions

A component schema that is itself a `oneOf`/`anyOf` — no `allOf`, no `properties` of its own, and not every non-null variant a string `const` (that is an enum; see Enum) — is a named union. It still becomes a `Model` (every component other than an enum or an array component does; see Array components below), and a `$ref` to it stays `{ kind: "model" }`, but the model carries the union: `variants` holds one `TypeRef` per non-null variant in document order, `compositionKind` says which keyword produced them, and `discriminator` is set when the union is discriminated. `fields` keeps what it always held — the inline variants' properties merged as optional fields (`UpdateOrganizationMembership`'s `role_slug` / `role_slugs`) — so an emitter that reads only `fields` sees the model it did before, while one that reads `variants` can emit a proper union type.

The variants are built exactly as the same union written inline is (`UnionType`): a `$ref` variant is a model or enum ref; an inline object variant is referenced by a model extracted for it; a nullable (`type: ['object', 'null']`) or multi-type (`['object', 'string']`) inline variant keeps its wrapper around that model; a primitive stays a primitive; a `type: 'null'` variant is dropped from `variants` — an inline union lifts it into a `nullable` wrapper, and a `Model` has no wrapper to carry it — so, as for a nullable enum component, the nullability travels on the reference instead: every `$ref` to a named union that admits `null` (a `type: 'null'` variant, a `type` list with `'null'`, or OAS 3.0 `nullable: true`) resolves to `nullable<model>`, the shape the same union written inline has. Every other variant — a primitive, an inline enum, an array, a map, an `allOf`, a nested union — is typed and extracted as the `variant_<n>` property of one synthetic object under the union's name, where n is the variant's 1-based position among the non-null variants, so whatever it mints is named `<Model>Variant<n>…` by the one rule a field's inline models follow (an inline enum second in the list is `PetVariant2`, an array's inline items third in the list are `PetVariant3`, a nested object under them `PetVariant3Child`), and two variants of the same kind can never share a name or a value list. When a name such a variant would mint is already a component's, or another named union's inline variant's, of a different shape, the context steps exactly as an array's or map's does beside a claiming sibling — `variant_1_item` / `variant_1_value` (`PetVariant1Item`, `PetVariant1Value`), then `variant_1_array_item` / `variant_1_member_value`, then numbered, with the same no-progress and attempt-cap guards — and every name nested under the variant moves with it, since both the reference and the extractor read the chosen context; a claimant of the identical shape is shared instead (the array's items then point at the component).

Inline object variants are named by the inline-variant rules with the union's model name as the base, except that the base itself is taken by the union's own model, so variant 0 steps off it like every later variant: a const-discriminator prefix (`CatPet` for `kind: cat`), its title as a prefix (`CircleShape`), the first property no other variant declares (`UpdateAuditLogsRetentionDtoWithRetentionPeriod` beside `…WithRetentionPeriodInDays`), else the position counter (`Pet1`, `Pet2`). Every component schema's name is reserved, so a variant can never shadow a component (a variant titled `Cat` beside a component `Cat` takes `CatPet`), and so is every context-free title another named union keeps for a variant of a different shape — the comparison sibling field unions already make (`schemaShapeKey`), read symmetrically: when `Circle` is `{ radius }` on `Shape` and `{ diameter }` on `Marker`, both fall back (`CircleShape`, `CircleMarker`) and the mappings follow; when the shapes are identical, both keep `Circle` and one model is emitted. The component schemas are one root for the depth rule above as well, so a title a field union nested in any component gives a different shape (`Drawing.marker.shape`'s `Circle` as `{ diameter }`) is contested for the named union too, and both fall back (`CircleShape`, `CircleDrawingMarkerShape`). Each variant and everything nested under it — objects with or without `type`, array items, map values, `allOf`s, nested unions, the members of a multi-type variant — is materialized by the same inline extractor a field's union variants go through, so a reference always has a model behind it. Each extracted variant model is a complete model of its own, so the union's merged fields and the variant's fields are typed independently (an inline `config` object appears as both `PetConfig` and `CatPetConfig`).

`discriminator` is resolved from the same sources, in the same order, as an inline union's, with a `$ref` variant's const read from the component it points at: an explicit `discriminator:` with a `mapping:` is the spec's own, each target reduced to the IR model name it refers to (the last `$ref` segment through `schemaNameTransform`, so `#/components/schemas/Cat` → `Cat`) — an entry pointing outside the variant list is kept as written, and an entry naming an inline variant's const redirects that variant's object member to its target, as it does inline, while the items or values of a multi-type variant's other members stay named from the model extracted for the variant (`PetWithKindItem`, never `CatItem`), so they always resolve; an explicit `discriminator:` without `mapping:` pairs each variant's const on the property with its model name (`{ cat: "Cat", dog: "Dog" }`), and is `{}` when any variant pins none, as it is inline; a `oneOf` with no keyword whose every variant is nameable (a `$ref`, a titled or inline object) is discriminated implicitly on the first property the first variant pins whose values are distinct across all of them — a constant every variant shares (`version: 'v1'`) is passed over, not taken as proof there is none. An `anyOf` is never discriminated implicitly, and the OpenAPI default of "the discriminator value is the schema name" is not synthesized. Mappings are built as own keys, so a value spelled like an inherited property (`constructor`) is neither rejected nor lost. As for an allOf+oneOf model, a set `discriminator` means emitters should dispatch on it, and its mapping values are IR model names. That is the one place the two forms differ. Both reduce `#/components/schemas/Cat` to `Cat`, but `Model.discriminator.mapping` holds IR model names — each target's last `$ref` segment through `resolveSchemaName`, so `cleanSchemaName` and the project's `schemaNameTransform` apply (`#/components/schemas/cat_dto` → `CatDto`, or whatever the transform makes of it), as an allOf+oneOf model's always has — while an inline union's `discriminator.mapping` only strips a leading `#/components/schemas/` and otherwise keeps each target as the document spelled it (`cat_dto` stays `cat_dto`; a target in another section, such as `#/components/responses/Cat`, stays whole). An emitter reading a named union's mapping can use its values as model names directly; one reading an inline union's mapping has to clean and transform them itself.

Three shapes are deliberately not unions. A `oneOf`/`anyOf` whose every non-null variant is a string `const` is an enum (see Enum). A `oneOf` written beside `properties` keeps today's object model (the properties are its fields; the branches are not read), and a component that is only a nullable wrapper around one plain inline object — `oneOf: [{ type: object, … }, { type: 'null' }]`, the object typed `object`, untyped, or `['object', 'null']` — stays the object its merged fields describe, as an inline wrapper collapses to `nullable<model>` rather than a union. A wrapper around one `$ref`, one primitive, or one object that also admits another type (`type: ['object', 'string']`) is a union of one, so the other type is kept.

Every pass that walks a model's type refs — reachability for emission, service assignment, ref rewriting and validation, dependency collection for imports, inline-enum promotion, the differ's direction index and model comparison, compat scoping, and the companion and parameter-group fingerprints — reads fields and variants alike through `collectModelTypeRefs`, so a model reached only as a variant is emitted, placed, and compared like one reached through a field. Every rename and fold goes through `renameModelRefs` and `renameTypeRefModels`, which repoint fields, variants and `discriminator.mapping` targets together — a union's mapping with the variant it names, by name in the Json fold and the list-envelope pass and by reference identity in the merge passes — and a `…Json` component folded onto its base carries its variants, composition keyword and discriminator onto the base as it carries its fields, so a union never silently becomes a plain object or keeps a dispatcher pointing at a name that is gone; a base that is a union the `…Json` model does not preserve — a named union's variants, keyword and discriminator, or an allOf+oneOf dispatcher's mapping, which may sit on a model with no fields — is not folded at all (both are kept, with a warning): two undiscriminated unions share the rule `oneOf`, so the variants are compared too, the `…Json` model's read as the fold would leave them — its model references under the base's name, as the fold renames them, while an enum reference or a literal is compared as it is, since the fold renames no enum and rewrites no value, so a base that accepts `PetState` is never handed `PetJsonState`; an identical union folds as before; and a component — a named union or a plain object — is never replaced by a same-named inline model, whatever its field count (see Models: the inline model shares the component only when the component admits it, and takes a qualified name otherwise). The fingerprints that decide whether two companions or parameter groups share one model include the variants and the dispatch rules (composition keyword, discriminator property and mapping), so two unions with the same members but different rules are kept apart. The differ reports a variant added (additive, like a new enum value), removed (breaking), a change of composition keyword between two unions (breaking), and any discriminator change (breaking) under `ModelModified.variantChanges`.

### Array components

A component schema that is an array — `type: 'array'`, an OAS 3.1 type list `['array', 'null']`, OAS 3.0 `nullable: true` beside `type: 'array'`, or `items` with no `type`, in every case with `items` declared (`isArrayComponentSchema`) — becomes no `Model`. A `$ref` to it resolves to the array the component declares, the shape the same array written inline has: with `Pets: { type: array, items: { $ref: Widget } }`, every `$ref` to `Pets` is `{ kind: "array", items: { kind: "model", name: "Widget" } }`, and a component that admits `null` wraps that in `nullable`, as a `$ref` to a nullable enum component is wrapped. This holds at every reference site — a component field, an `allOf` member (`allOf: [{ $ref: Pets }]`, with or without limits beside it), a named union's variant, a request body, a parameter in any location, a response header, a success, error, `default` or range response body, a webhook payload — because every site types a `$ref` through `schemaToTypeRef`; and a list envelope whose data array is a `$ref` to an array component, under any nullable wrapper, is detected and unwrapped as one whose array is written inline, iterating the component's items. `spec.models` holds no `Pets`, so an emitter never sees an empty class, or a list typed as one object.

What the items reference is extracted under the component's name, by the inline extractor a field's array goes through, as the `item` property of a synthetic object under the component: an inline object item is `<Component>Item` (`PetsItem`), with everything nested under it named from that (`PetsItemOwner`); the object variants of an `items.oneOf` are named by the inline-variant rules from `PetsItem` (`PetsItem`, `PetsItemWithSide`); an inline enum is `PetsItem`, lifted into `spec.enums` whether or not anything refers to the component (an inline object item's model is likewise emitted for a component nothing refers to); the objects of a nested array or map are `PetsItem` too, by the one rule a field's items and values follow. The component's name is the one `cleanSchemaName` and `schemaNameTransform` give it, so a component `pet_list` renamed to `PetCollection` gives `PetCollectionItem`. A `$ref` item mints nothing: it stays a reference to its model or enum, and a `$ref` to another array component resolves in turn (`array<array<Widget>>`). Every name the whole tree mints — the item model, an object nested under it (`PetsItemOwner`), an inline enum a nested field holds, a union variant — is read off a rehearsal of the extraction itself before any plan is decided, so a nested name counts exactly as the item model's does. When any of them is already claimed for a different shape — by a component model (compared by `modelFingerprint`), a component enum (by its members), an array component's own name, another array component's tree, or another named union's inline variant — the whole tree's context steps exactly as a named union's `variant_<n>` does (see Named unions): `item_item` (`PetsItemItem`, `PetsItemItemOwner`), then `item_array_item`, then numbered, until no name under it is claimed; a claimant of the identical shape is shared, and the tree references it. Each tree's names are read in isolation under `item` for the others' claims, so two trees that mint one name decide symmetrically — both keep it and one model is emitted when the shapes agree, both step when they differ — and the decision does not depend on declaration order. The reference and the extractor read one plan, decided once per document before any reference is typed, so the two agree.

A component whose items reach back to it — `Tree: { type: array, items: { $ref: Tree } }`, directly or through another array component — has no finite type in the IR: the inner reference is typed as `unknown` (`array<unknown>`), with one `[oagen] Warning:` per component however often it is referenced.

The component's own `description`, `deprecated` and `externalDocs` sit on no model, and each node reads them from where it always has. A parameter whose schema is a `$ref` to the component takes the component's `description`, `deprecated`, `default`, `example` and `externalDocs` as fallbacks and merges the component's limits (`minItems`, `maxItems`) underneath its own. A field reads its own schema for `description`, `deprecated`, `externalDocs` and `constraints` — a bare `$ref` field has no `constraints` and does not carry the component's flag, and a `description` written beside the `$ref` is the field's — and takes the component's `example` and `examples` when it declares none. The items' own keywords are the item model's, as for any inline object.

Two shapes are not array components. A `type: 'array'` with no `items` still becomes a fieldless model, and a `$ref` to it stays `{ kind: "model" }`, since `schemaToTypeRef` types the inline form as `unknown` with a warning. A composition beside the array — an `enum:` list, a `oneOf`/`anyOf` with a typing variant, an `allOf` with a `$ref` member or a member with `properties` — is read first, as `isArraySchema` reads it, so such a component is what the composition makes it (an enum, a named union, an `allOf` model), as before.

### Inline model naming

Models come from `components/schemas` (named as written, after `cleanSchemaName` and any `schemaNameTransform`; an enum or array component yields none — see Enum and Array components) and from inline object schemas in operations, which the parser materializes as models so emitters have something to reference. An inline request body or response is named from its operation:

- **With an `operationId`:** `PascalCase(operationId)` + `Request` / `Response`, passed through `cleanSchemaName`. `createNote` → `CreateNoteRequest` / `CreateNoteResponse`.
- **Without an `operationId`:** from the full path and method. Each non-parameter segment is PascalCased in order, each `{param}` segment becomes `By` + `PascalCase(param)`, a custom method written after a colon is read as its segment followed by the verb (`POST /pets/{id}:adopt` → `PetsByIdAdoptPostRequest`, the prefix of `/pets/{id}/adopt`), then the method and `Request` / `Response` are appended, and the whole name is normalized with `toPascalCase` so an operation's body and response share a prefix (`POST /a/b` → `AbPostRequest` / `AbPostResponse`). `POST /notes` → `NotesPostRequest` / `NotesPostResponse`; `POST /notes/{id}/pin` → `NotesByIdPinPostResponse`; `GET /users/{user_id}/sessions` → `UsersByUserIdSessionsGetResponse`. This tells the common path shapes apart (list vs. item, sibling and nested sub-resources) but is not unique by construction: `/foo-bar` and `/foo/bar`, `/notes/by-id` and `/notes/{id}`, `/notes` and `/notes/`, or `/pets/{id}:adopt` and `/pets/{id}/adopt` flatten to the same words. Names already taken are reserved first: every component schema name and, for every operation with an `operationId`, the stem all of its models start with (`PascalCase(operationId)` after `cleanSchemaName`). A path-based prefix is treated as colliding when any reserved name starts with it, because one prefix is the stem of several emitted names (`…Request`, `…Response`, a list's `…Item`, nested inline models such as `…ResponseOwner`, envelope companions such as `…ListMetadata`). Names derived from a path-based prefix use it verbatim — body `oneOf` variants included (`NotesPostRequest`, `NotesPostRequest2`, `EmailNotesPostRequest`) — and are never re-cleaned, so no later step can move them out from under the reservation; as a second line of defence the check also runs on the cleaned spellings of the prefix (`cleanSchemaName`, the project's `schemaNameTransform`, `ListItem`-marker stripping), so an unnamed `GET /notes` also yields to a component `NoteGetItem`. Names that embed the prefix behind a const value are covered as well: a body `oneOf` variant pinning `kind: email` is `EmailTagsPostRequest` and a nested `oneOf`/`anyOf` variant is `<Const><Parent><Field>`, so every string `const` (or single-value `enum`) found in the operation's inline body and 2xx response variants, top level and nested, is prepended to every spelling before the check, and a hashed prefix lands inside those names too (`EmailTags151Dd5PostRequest`). Names that do not embed the prefix at all — a response `oneOf` variant named from its bare const (`Email`) or a `title`-mapped variant — are outside what a disambiguator can separate and are left as they are. This is deliberately a superset: a component `AuditEventsGetter`, or an operationId `auditEventsGetSummary`, also pushes an unnamed `GET /audit/events` onto a hashed name although no emitted name would coincide; determinism and never sharing a name wrongly matter more than the rare extra hash. The reservation is unconditional, so an inline body is never merged into a same-named component even when their shapes agree. When two distinct paths with the same method would collide, the path spelled most plainly keeps the plain name (no trailing slash, `{id}` rather than a literal `by-id`; precisely, the lowest `[trailing slash, segments other than a bare parameter with a character outside a-z0-9]`, so a custom method's colon counts and `/pets/{id}/adopt` keeps the plain name over `/pets/{id}:adopt`), and every other path in the group gets a six-character disambiguator derived from its raw path (the start of its SHA-1, inserted before the method): `POST /foo/bar` next to `POST /foo-bar` → `FooBarPostResponse` and `FooBar546F12PostResponse`; `GET /notes/{id}` next to `GET /notes/by-id` → `NotesByIdGetResponse` and `NotesByIdBa41B5GetResponse`. When two paths tie for plainest (`/foo-bar` and `/foo_bar`), or the path-based name matches a reserved one (an unnamed `POST /audit/events` next to `operationId: auditEventsPost` or next to `components/schemas/AuditEventsPostRequest`), nobody keeps the plain name and every path in the group is disambiguated. The result depends only on the document's paths, `operationId`s and component names and never on their order; `operationId`-derived and component names never change, and paths that do not collide keep the plain name.
- **Shared through `components/responses`:** a response written as `{ $ref: '#/components/responses/PetFound' }` is resolved before it is read (chains are followed; a circular chain fails the parse; a ref nothing under `components/responses` answers — one into another section, or a bundler-written pointer such as `#/paths/~1pets/get/responses/200` — is warned about and read as written, with no body or headers, as before refs were resolved; a sibling `description` beside the `$ref` wins in an OAS 3.1 document, outermost first, and is ignored in an OAS 3.0 one). Its inline body is named after the component, not the operation — `PascalCase(componentName)` + `Response`, passed through `cleanSchemaName`, the suffix not doubled when the component is already named `…Response` (`PetFound` → `PetFoundResponse`, `ErrorResponse` → `ErrorResponse`) — so every operation that returns it shares one model instead of minting a `<Op>Response` copy each; a chain is named after the ref the operation wrote. The component's stem is reserved like an `operationId`'s, so an unnamed `GET /owner` beside a component response `OwnerGet` takes a hashed name. The component's headers resolve through `components/headers` as inline ones do.

A response object with a string `const` discriminant (`object: "note"`) is named from that value instead (`Note`); nested inline objects are qualified with their parent model's name. The items of an array primary success body (`Operation.response`: `type: 'array'` or bare `items`, nullable in any spelling or not; a secondary media type's, fallback or error body keeps its own name, `ListPetsApplicationVndPetJsonResponse`, `ListPetsError409`) and of a list envelope's data array are typed as a field named `<Op>Item` — the `Response` suffix replaced with `Item` — under no parent, whatever their shape, so every model they reference is created under the name the reference uses: a plain object is `ListPetsItem`; a nullable object is `nullable<ListPetsItem>`; the inline object variants of a `oneOf`/`anyOf` take the union's names from it (`ListPetsItem`, `ListPetsItemWithSide`, `CircleListPetsItem`); an inline enum is `ListPetsItem`; the objects of a nested array or map, and anything under any of these, are qualified under it (`ListPetsItemOwner`); a `$ref` stays the reference and mints nothing. A request body or parameter that is an array is typed as the body or parameter itself, so its inline object items are `CreatePetsRequest` and `PetsFilter`, not `…Item`.

If two inline models still resolve to the same name with different fields or field types (two `operationId`s that PascalCase to the same word, for example), the parser keeps the one with more fields — the first definition on a tie — and prints `[oagen] Warning: Inline model "…" has more than one definition with different fields or field types`.

An inline model that resolves to a component schema's name — a request body or response named from its operation or pinned by an `object` const, a component field's object, a nested object, an array's items, a `oneOf` variant, a header, fallback, error or secondary-body model — shares the component only when the component admits it: the same field names; each field the same type, limits, default, access flags and `deprecated`; the component allowed to be looser on requiredness (a field the inline model requires may be optional on the component) and on the field type's own nullable wrapper (non-null on the inline model, `nullable<…>` on the component), never stricter; and the models' own limits, type parameters, variants, dispatch rules and `deprecated` identical. The inline model is then dropped and its references resolve to the component. Otherwise the inline model takes a name qualified by its site — the operation's name prefixed (`GetWidgetWidget` for a `getWidget` body pinned by `object: widget`), a numeric suffix when the name already starts with it (`GetPetResponse2` for the `getPet` body, `CreateNoteRequest2` for the `createNote` body), `PetOwner2` for a field object of `Pet`, the shape registry's own candidates for a header, fallback, error or secondary body (`ListPetsDefaultResponse2`) — and the merge passes say so: `[oagen] Renamed inline model "GetPetResponse" → "GetPetResponse2": its shape differs from component schema "GetPetResponse"`. A component is never replaced: every operation that `$ref`s it keeps the shape the document declares, whatever an inline model of the same name adds, and the component's `description`, `externalDocs` and `deprecated` stay its own. Nested models are decided before their parents, so a parent whose child was renamed references the renamed child and, no longer admitted by the component of its name, is renamed with it (`GetPetResponse2 { owner: GetPetResponseOwner2 }`). The components' own inline field models are settled first, before any operation or webhook is read, so every later comparison with a component — the shape registry's, the merges' — reads the component's children by their final names: when `GetPetResponse.owner` is an inline object and a component `GetPetResponseOwner` of another shape exists, the field object becomes `GetPetResponseOwner2` at once, and a `getPet` body whose `owner` `$ref`s `GetPetResponseOwner` is not admitted by the component and keeps the reference it declared, under `GetPetResponse2`; a reference an operation's or webhook's `allOf` merge copies from such a field is created under the settled name. A webhook's models have a site of their own, qualified by the webhook's stem (`PetAdoptedComp` for a payload variant titled like a component of another shape). A rename repoints every reference kind alike (`renameTypeRefModels`): a union's `discriminator.mapping` follows its renamed variant, in a field, a response, a payload or a header. A model the parser could not rename — none the parser produces; a direct caller of the merge passes that gives no site — is dropped in favour of the component, with a warning.

**Inline `allOf`.** An inline schema composed with `allOf` is merged into one model by a single reading (`mergeAllOfMembers`), wherever it appears: a request body, a response body of every kind (primary, secondary media type, error, `default` and range), a response header, a webhook payload or parameter, a component or inline model's field, array items, map values, a union's `allOf` variant, and a field nested under a discriminated component variant. Members are read in document order. A `$ref` member contributes its component's properties (those of the component's own `allOf` chain included). A model built from the merge (`materializeMergedAllOf`: a field anywhere, a field nested under a discriminated component variant) types each inherited property as the component's model types it (`Base.meta` stays `BaseMeta`) and does not read into it again, so a component that extends itself through a field (`Node.child: allOf: [{ $ref: Node }, …]`) is typed as the `NodeChild` that exists; a primary response body types inherited properties under its own name. A ref no component schema answers contributes nothing (a response whose only `$ref` is unanswered is typed as that reference). An inline member contributes its own properties, those of its nested `allOf` members and, for a `oneOf`/`anyOf` member, those of every inline object variant — read through the variant's own `allOf` members and nested unions the same way — as optional fields: `allOf: [{ properties: { name }, required: [name] }, { oneOf: [{ properties: { ownerId } }, { properties: { shelterId } }] }]` is `{ name, ownerId?, shelterId? }` inline exactly as it is as a component. A variant's `required` list is not read, since its properties are present only on that branch; a `$ref` under a variant — the variant itself, or a member of the variant's own `allOf` — is not followed (its component keeps its fields); and a union a `$ref` member's component carries is not read (that component's own model dispatches or flattens it). A property keeps the first declaration an always-applying member gives it, whatever a variant says; a property only variants declare is typed as the union of its distinct declarations (documentation ignored): one shape is that declaration, several shapes are a `oneOf` of them read as any inline union is — `kind: { const: cat }` beside `kind: { const: dog }` becomes an inline enum `<Model>Kind`, `const: true` beside `const: false` a union of literals, two inline objects a union of two variant models — so a field is never typed from one variant's value alone. A field reads its flags, documentation and limits from its own schema, never from a union's variants, so the combined declaration carries every such keyword the declarations agree on, value for value — `readOnly`, `writeOnly`, `deprecated`, `description`, `default`, `example`, `examples`, `externalDocs` and the validation keywords: two `kind` declarations both `readOnly: true` with different consts make a read-only enum field; a keyword the declarations disagree on, or only some declare, is not the field's. A `null` any declaration admits (`nullable: true` or a `type` list naming it) is a value the property takes on that branch, so the combined declaration admits it (`nullable<enum>`, `nullable<union>`). The declarations themselves are kept as written inside the union, so an enum member or a variant model still carries its own description and limits. A schema reached twice is read once in each capacity: an object shared between a variant and a member (a YAML anchor, an object a `transformSpec` hook reuses, a `$ref` written twice) still contributes its `required`, and is still followed, when the member is reached. An inline `allOf` is always flattened: the dispatcher form — a `discriminator` whose mapping names one model per variant — is built for component schemas only. Whether an `allOf` mints a model at all is one question asked everywhere (`declaresInlineProperties`): a member that declares properties inline, its own or through a nested `allOf` member or union variant, makes `allOf: [{ $ref: Base }, { oneOf: [...] }]` an augmentation model `<Parent><Field>` with `Base`'s fields and the variants', not a bare reference to `Base`.

### Field Examples

OpenAPI 3.1 deprecates a schema's `example` in favour of the JSON Schema `examples` list. The parser reads both: `examples` carries every value the document gives, and `example` is the document's `example` when present, otherwise the first entry of `examples`. A field whose schema is a `$ref` to a component falls back to that component's `example`/`examples`, the same way a parameter does. A field whose schema (and `$ref` target, if any) gives neither has no `example` and no `examples` key.

### Constraints

JSON Schema's validation keywords are carried on `Field`, `Parameter` and `Model` so an emitter can document a value's limits ("at most 100"), check a value before sending it, or keep a generated example within range. `type`, `enum`, `const` and `required` already have their own place in the IR and are not repeated here.

```typescript
interface Constraints {
  // numbers
  minimum?: number;
  maximum?: number;
  exclusiveMinimum?: number;
  exclusiveMaximum?: number;
  multipleOf?: number;
  // strings
  minLength?: number;
  maxLength?: number;
  pattern?: string; // ECMA-262 regex, verbatim from the document
  // arrays
  minItems?: number;
  maxItems?: number;
  uniqueItems?: boolean; // present only when true
  minContains?: number;
  maxContains?: number;
  // objects
  minProperties?: number;
  maxProperties?: number;
  dependentRequired?: Record<string, string[]>;
}
```

Every member is optional and present only when the document declares it. A schema with no validation keyword yields no `constraints` key at all, so `field.constraints?.maxLength` is the idiomatic read. The parser ignores a keyword whose value has the wrong type (a string `maxLength`, say) rather than carrying it.

**OAS 3.0 → 3.1 normalization.** OpenAPI 3.1 (JSON Schema 2020-12) gives `exclusiveMinimum` / `exclusiveMaximum` as the bound itself; OpenAPI 3.0 spells them as booleans that make `minimum` / `maximum` exclusive. Both versions are parsed, and the IR always uses the 3.1 shape:

| Document (3.0)                             | IR                                         |
| ------------------------------------------ | ------------------------------------------ |
| `minimum: 0, exclusiveMinimum: true`       | `{ exclusiveMinimum: 0 }` (no `minimum`)   |
| `maximum: 100, exclusiveMaximum: true`     | `{ exclusiveMaximum: 100 }` (no `maximum`) |
| `minimum: 0, exclusiveMinimum: false`      | `{ minimum: 0 }`                           |
| `exclusiveMinimum: true` with no `minimum` | nothing                                    |

A 3.1 document's numeric form passes through unchanged, including the legal-but-unusual case of an inclusive and an exclusive bound on the same side.

**Scope.** The keywords declared on the field, parameter or model schema are collected, conjoined with those of its inline `allOf` members: the parser unwraps a single-member `allOf`, so `{ allOf: [{ type: string, maxLength: 3 }] }` is a string field carrying `{ maxLength: 3 }`, and a `$ref` member contributes the keywords written beside the reference while the referenced model keeps its own. Limits nested inside array `items` or map values (e.g. `items: { maxLength: 10 }`) are not carried. The one exception is a nullable wrapper — a `oneOf`/`anyOf` with exactly one non-null, non-`$ref` branch, which the IR collapses to `nullable<T>` — whose branch keywords are conjoined with the wrapper's own (and its `allOf` members'), so `anyOf: [{ type: string, maxLength: 8 }, { type: "null" }]` gives `{ maxLength: 8 }` and `{ allOf: [{ maxLength: 30 }], anyOf: [{ type: string, minLength: 20 }, { type: "null" }] }` gives `{ maxLength: 30, minLength: 20 }`, and an inline model built from that branch carries the same conjoined keywords, so `minProperties` written beside `anyOf: [{ type: object, … }, { type: "null" }]` reaches both the field and its model. Limits on a general multi-variant union are not carried. Keywords written beside a `$ref` (OpenAPI 3.1 allows them) are the field's own and are kept; a bare `$ref` field gets no `constraints`, because its limits belong to the referenced model. A `Model` carries whatever its own schema declares — for an object schema that is `minProperties`, `maxProperties` and `dependentRequired`; for an `allOf` model — a component, or an inline response, request body or field the parser rebuilds from `allOf` members — it is the wrapper's keywords conjoined with its members' (the stricter bound wins; a `$ref` member contributes the keywords written beside the reference, while the referenced model keeps its own). A variant model of a discriminated `allOf` + `oneOf` union conjoins the shared keywords — the outer wrapper's, the base members' and any written beside the `oneOf` — with the variant's own the way `allOf` does — an instance must satisfy both, so the larger `min*` and the smaller `max*` win and `dependentRequired` maps are unioned per property.

### Deprecation

`Model.deprecated` and `Enum.deprecated` are present, and `true`, only when the schema the type was built from says `deprecated: true` — the literal `true`; any other value (`"yes"`, `1`) is not a declaration; the key is absent otherwise, as on `Operation`, `Parameter`, `ResponseHeader` and `Field`, each of which reads the keyword from its own source by the same rule (listed at the end of this section). Which schema that is, per model:

- A component schema: its own top-level keyword. For an `allOf` component it is the wrapper's; a member's flag is not read — a `$ref` member's stays on the referenced model, so `Composed: { allOf: [{ $ref: Legacy }, …] }` is live while `Legacy` is deprecated, and an inline member's is dropped, as `Field.deprecated` drops it on a field.
- A discriminated `allOf` + `oneOf` union: the wrapper deprecates the dispatcher model; each variant model carries its own variant's flag.
- An inline object that becomes a model — a request body, a `oneOf` body variant (a discriminated body takes the wrapper's flag, since the variants merge into one model), a response (an `allOf` response takes the wrapper's flag), a nested field object, array items, map values, a field's `oneOf` variant — carries that schema's flag. A multi-variant union is never collapsed, nullable or not (`type: ['object', 'null']` beside a `oneOf` included): each variant model is built from its variant, with the variant's own flag, and the wrapper's flag stays on the field. A field spelled `{ deprecated: true, anyOf: [{ type: object, … }, { type: "null" }] }` or `{ deprecated: true, allOf: […] }` carries its wrapper's flag onto the model built from the branch or the merge, the same way its `constraints` travel, so the nullable and composed forms match the direct-object form — and only the wrapper's: a flag written on the null-wrapped branch or on an `allOf` member is not read, exactly as `Field.deprecated` does not read it.
- A `<Name>Json` model folded into `<Name>` does not carry its flag over: deprecation names the type the SDK exposes, and `<Name>` keeps its own. A live `<Name>Json` is never folded onto a deprecated `<Name>` — every live reference to it would then resolve to a deprecated type — so both models stay, and the parser says so.

An inline enum (one declared on a field, parameter or header rather than under `components.schemas`) carries no flag of its own: the IR reaches it through an `EnumRef`, and the field or parameter that declares it carries `deprecated`.

Wherever two inline models are folded into one by structural agreement — list-envelope companions sharing a bare name, header models sharing a registry entry, same-named inline models in the merge passes — `deprecated` is part of the shape, and a deprecated copy never shares a live model's name. An envelope companion keeps its operation-qualified name (`ListLegacyUsersListMetadata`) while the live copies share the component or majority name, and a header model gets a qualified name of its own. A reference a header, secondary-body, fallback-body or error-body schema wrote by sharing a primary body's or a companion's model (its shape matched the name's owner) belongs to that model's site too, so renaming the model repoints the `default` response or header along with the site's own references. In the merge passes, a live copy owns a shared name: when a deprecated inline model and a live one would resolve to the same name — two inline responses pinned by the same `object` const, an inline request body or a component field's object named like another — the deprecated copy is folded onto the live definition only when it is identical to every live copy of that name in everything but the flag (fields, requiredness, types, limits, defaults), with a warning; a copy that differs in anything else, requiredness included, keeps its own model under a qualified name — its operation's name prefixed (`GetLegacyWidgetWidget`), or, when the name already starts with it, as a request body named from its operation does, a numeric suffix (`CreateNoteRequest2`); a component field's object likewise takes a suffix (`PetOwner2`) — minted against every model and enum name in the document (inline enums the collectors lift later included), and only the references minted for that copy are repointed — by identity, never by name: an explicit `$ref` to a same-named component stays as written even in the same response map, a reference an `allOf` merge copied from another component's field follows that field's model, and nested models are named before their parents, so a parent whose child was just renamed is no longer "identical but for the flag" to its live twin. A component's name and flag are authoritative, in both directions: an inline model named like a component whose flag differs — an inline response, a request body, a field object, array items, a `oneOf` variant — takes a qualified name the same way, whatever its shape, so a live field never resolves to a deprecated component (`Pet.owner` → `PetOwner2` beside a deprecated `PetOwner`) and a deprecated inline copy never folds onto a live component. An inline response that resolves to a component's name with the same flag shares the component when the component admits its shape and takes a qualified name otherwise (see Models); the component's fields, `deprecated`, `description` and `externalDocs` are never replaced. So two things never depend on document order: whether a reference reaches a deprecated model — only where the document itself wrote `deprecated: true`, on the component or on that very operation's or field's own schema, never because of folding — and the name a deprecated copy takes: the shared name when it is identical but for the flag to every live copy of that name, its own qualified name otherwise (when the live copies disagree among themselves, the deprecated copy is always qualified). What still follows document order, exactly as on `main`, is which live definition a shared name carries when the live copies disagree — the first declared, or the one with more fields — and, for a list-envelope companion several operations share, which of them qualifies it (the operation the envelope pass made its owner: the first declared of the most common shape).

**Source per node.** Each node reads `deprecated` from one place: `Operation` from the Operation Object's own keyword; `Parameter` from the first truthy of the Parameter Object (after a `components.parameters` `$ref` is resolved), its inline `schema`, then the component schema its `schema.$ref` points at, so a `false` on an earlier level does not stop a `true` on a later one; `ResponseHeader` from the Header Object only (after a `components/headers` `$ref` is resolved), never from its schema; `Field` from the property schema itself, a keyword written beside a `$ref` included, while the referenced model keeps its own and an `allOf` member's is not read; `Model` and `Enum` from the schema's own top-level keyword as described above. At every site the parser tests `=== true`: a `false`, absent or non-boolean keyword (`"yes"`, `1`) leaves the key absent, so the IR never carries anything but a literal `true`, on any of the six nodes. `EnumValue.deprecated` reads the value's own `const` member — an enum declared as a `oneOf`/`anyOf` of `const` schemas — by the same `=== true` rule, and is absent on every value of a plain `enum:` list, which has no per-value keyword (see Enum below).

The differ compares the flag on every node that carries it — operation, parameter, model, field, enum, enum value, webhook and webhook parameter — and reads it the way the parser writes it: only `true` is deprecated, so `false` and an absent key are the same thing, and a document that spells out `deprecated: false` diffs as unchanged against one that omits it. A flip is reported on the owning `-modified` change: `deprecatedChanged: true` on `operation-modified`, `model-modified`, `enum-modified` and `webhook-modified`, with `oldDeprecated`/`newDeprecated` beside it (present exactly when the flag is); a `param-deprecated-changed`, `field-deprecated-changed` or `value-deprecated-changed` entry, carrying the same two values and a `details` that reads `live → deprecated` or `deprecated → live`, in the change's `paramChanges`, `fieldChanges` or `valueChanges` for an operation's or a webhook's parameter, a field or an enum value. A model, enum, operation or webhook whose only change is the flag is still reported, with an empty nested list. Becoming or ceasing to be deprecated changes no contract — the node is still there with the same shape — so every one of these is additive, in either direction; it still counts as `modified` in the summary, and a breaking change on the same node (a removed field beside the model's flag, a changed response beside the operation's, a retyped payload beside the webhook's) keeps the change breaking. Each flip is also mirrored into `behaviorChanges` as a `deprecated-changed` entry naming the node (`operation`, `parameter`, `model`, `field`, `enum`, `enum-value`, `webhook` or `webhook-parameter`) and copying `oldDeprecated`/`newDeprecated` from the change, the way a parameter default change is, so a changelog can say which way it went without reading both specs. Parameters are matched by location and name, since a path `id` and a query `id` may sit on one operation and a webhook's header and query parameters may share a name, and every `paramChanges` entry carries `paramLocation` to say which one it is about. A response header's flag is not compared, since the differ does not compare response headers.

## Enum

```typescript
interface Enum {
  name: string; // PascalCase
  description?: string; // The component enum schema's own `description`, when it has non-whitespace content; a lifted inline enum carries none
  values: EnumValue[];
  externalDocs?: ExternalDocs; // The enum schema's externalDocs, when usable — a component's, or the inline schema's the enum was lifted from
  deprecated?: boolean; // The component enum schema's own `deprecated: true`; absent otherwise
}

interface EnumValue {
  name: string; // UPPER_SNAKE_CASE display name
  value: string | number; // Actual value from spec (preserves numeric types)
  description?: string; // The value's own documentation (a const member's `description`, else its `x-enum-descriptions` / `x-enumDescriptions` entry); absent otherwise
  deprecated?: boolean; // `true` when the value's const member says `deprecated: true`; absent otherwise
}
```

**Two spellings declare an enum.** An `enum:` list, and — the OAS 3.1 way to document or deprecate values one by one — a `oneOf`/`anyOf` whose every non-null variant is a string `const` schema (a single-member string `enum` counts as a const). Under `components.schemas`, both become an `Enum`, and a `$ref` to either resolves to `{ kind: "enum" }`; a `oneOf` of consts there is an enum, not a named union, so `PetStatus: { oneOf: [{ const: "available" }, { const: "sold" }] }` is `enums[].PetStatus` with no `PetStatus` model. The same `oneOf` written inline on a field, parameter or header collapses to an inline enum (one of two or more consts; a single const with no `enum:` list beside it stays a `literal`), as it did before. A union with any other variant — a `$ref`, an object, a number const — is a union, as before, and a `oneOf` written beside `properties` or an `allOf` is not an enum. An `enum:` list written beside a `oneOf`/`anyOf` of consts applies together with it, as JSON Schema keywords do: the members are the consts whose value the list allows (a const the list leaves out is dropped, with its documentation), and a `type: 'null'` variant admits `null` only when the list does not leave `null` out — so `{ enum: ["a"], oneOf: [{ const: "a" }, { const: "b" }, { type: "null" }] }` is the one-value enum `a`, not nullable. Inline, the list is read the same way whatever it leaves — the members `constUnionEnumMembers` keeps and the nullability `enumListAdmitsNull` decides, the two helpers the component path reads: one member left is an inline enum of that member, none left is an inline enum with no members (as an empty `enum:` list is), never the union of every const the list forbade — so that schema on a field is the one-value inline enum `a`, not nullable, exactly as the component is. The component's own `description` is `Enum.description`, as a model's is `Model.description`; a lifted inline enum carries none, since that schema's text is the field's or parameter's.

**Per-value documentation.** Each `EnumValue` carries what the document attaches to that one value. `description` is the const member's own `description`; a value whose own text has no content — every value of an `enum:` list — takes its entry from the enum schema's `x-enum-descriptions` or `x-enumDescriptions` extension. Either key may hold an object mapping each value's text form (`"5"` for a numeric `5`) to its description, or a list aligned with the members as written (the `enum:` entries, or the `oneOf`/`anyOf` variants, a `null` entry or `type: 'null'` variant counted in its place); `x-enum-descriptions` is read when it holds an object or a list, `x-enumDescriptions` otherwise. Text reaches the IR only when it has non-whitespace content; the key is absent otherwise. `deprecated` is present, and `true`, only when the value's const member says `deprecated: true` — the literal `true`, as on every other node — so a value of an `enum:` list never carries it. Members are read by occurrence, not by value: a `oneOf`/`anyOf` that repeats a const yields one `EnumValue` per branch, each with its own documentation, inline and under `components.schemas` alike. Nullability is never a member: a `null` entry or a `type: 'null'` variant makes a `$ref` to the component resolve to `nullable<enum>`, as before.

**Inline enums sharing a name.** When two inline enums lift to one name, the first lifted gives the enum its value descriptions, as it gives its link. Per-value deprecation is part of the members, not documentation: a second copy with the same values that deprecates a different one is renamed (`PetsMode2`) before it is promoted, as a copy with other values is, so a field whose schema does not deprecate a value never resolves to an enum that marks it. Every pass that compares shapes to decide whether two models are one reads an inline enum the same way — each value with its deprecation (`shapeWithEnumFlags`, `enumShapeKey`): the materialization fingerprint header and body models share a registry entry by, the merge passes' identical-shape checks and the `<Name>Json` fold, the named-union shape key, and the companion and parameter-group fingerprints — so a copy differing only in that keeps its own model name, as a deprecated copy of a model does. The raw-schema comparison that lets two sibling inline objects share one model, or two unions' variants share a title (`schemaShapeKey`), reads `deprecated: true` as shape at every level for the same reason, a const member's included. The member key is a JSON pair of value and flag, so a live `"active!deprecated"` and a deprecated `"active"` never read alike, and a member list is compared as a complete sorted list, so a repeated member counts each time it occurs: `[a, a!, b]` and `[a, a, b]` are different types. With `--doc-url`, `Enum.description` has its relative links expanded exactly as `Model.description` and every `EnumValue.description` do.

## ErrorResponse

```typescript
interface ErrorResponse {
  statusCode: number; // e.g., 401, 404, 422
  type?: TypeRef; // Response body type, if any
  headers?: ResponseHeader[]; // e.g. Retry-After on a 429; only when the spec declares at least one
  description?: string; // e.g. "Not found"; only when it has non-whitespace content
  contentTypes?: string[]; // Media types under `content`, in document order; only when they add to `type` (see below)
  contents?: ResponseContent[]; // One per contentTypes entry, same order; the application/json entry shares `type`
}
```

`type` is the JSON body — `application/json` by essence, else a `+json` media type such as `application/problem+json` — read as a fallback body's is. A `$ref` body is a plain reference to the component model; an inline body is materialized into `spec.models` under an operation-qualified name so that two operations' inline `404`s never share one model, nor do two status codes of one operation: `<Op>Error<code>` from the `operationId` (`getPet` + `404` → `GetPetError404`), or the path-derived prefix plus `Error<code>` without one (`GET /pets/{petId}` → `PetsByPetIdGetError404`); a body that came from `components/responses` is named after the component instead (`<Component>Response`), shared by every operation that returns it. Nested objects, array items, `oneOf`/`anyOf` variants and map values under the body follow the usual inline-model naming rules from that name (`GetPetError404Details`, `GetPetError404WithCode`). The body is typed through the same deferred mechanism as a response header or a `default` body (see [Default and Range Responses](#default-and-range-responses)): it is named only once every operation's request-body and primary-response models are known, against the spec-wide registry of model shapes, so a name a component schema, a model nested in one (`GetPet.error404` owns `GetPetError404`), or an earlier header, fallback or error model already owns with a different shape moves the whole body to the next free name (`GetPetError404Body`, then `GetPetError404Body2`, …), nested models and reference together; an identical shape shares it. A `oneOf` variant named by its bare title (`Circle`) that clashes is reserved and takes its qualified name exactly as when a sibling owns the title (`CircleGetPetError400`), while a `$ref` inside it keeps its component; a titled variant nested below the top level is renamed under the body (`GetPetError400Circle`) with every reference rewritten. A body that is itself an inline enum, or an array of one, is promoted to `spec.enums` under the same name; one a component or header enum owns with other members, or a model owns (another same-stem operation's inline `404`), steps to `GetPetError404Body`. An enum nested in the body (`GetPetError422Severity`) is promoted with every other model's field enums: one a component enum owns with other members is numbered (`GetPetError422Severity2`), identical members share. Two operations with identical inline bodies get two models, exactly as they get two `<Op>Response` models.

```typescript
// The `default` response: every status the operation does not list.
interface DefaultResponse {
```

## Operation Resolution

Source: `src/ir/operation-hints.ts`

The operation resolver derives method names, mount targets, and wrapper metadata for all operations in the spec. It runs in `buildEmitterContext()` and produces `ResolvedOperation[]` on `ctx.resolvedOperations`.

### Algorithm

`deriveMethodName(op, service)` derives a snake_case name from the HTTP method and path:

1. Strip path-param segments (`{id}`, `{slug}`, etc.)
2. If the terminal segment is an action verb (`verify`, `enroll`, `confirm`, `revoke`, etc.), use it as the verb with the preceding resource as the noun: `verify_challenge`
3. Otherwise, use a CRUD verb from the HTTP method: GET → `list`/`get`, POST → `create`, PUT/PATCH → `update`, DELETE → `delete`
4. Singularize the resource noun for single-resource operations

### Hint types

### Mount rules

Service-level remounting maps an IR service name to a target namespace. All operations in the source service are mounted on the target unless overridden per-operation. Per-operation `mountOn` hints take precedence over service-level rules.

Rule keys may be exact service names or trailing-`*` prefix patterns. Precedence: an exact key always wins; otherwise the wildcard with the longest prefix wins. Matching is plain `startsWith` string comparison — `*` is only meaningful as the final character, and no regex is involved. This lets a family of tags collapse to a few rules:

```typescript
{
  "UserManagement*": "UserManagement",                          // catch-all for the family
  "UserManagementOrganizationMembership*": "OrganizationMembership", // longer prefix wins
  "UserManagementDataProviders": "Pipes",                       // exact wins over wildcard
}
```

Note that a catch-all also absorbs future tags added to the spec under that prefix — a new `UserManagementFoo` tag mounts silently instead of surfacing as a new top-level service, so review `oagen diff` output (or run `/oagen:review-operations`) when the spec adds tags.

### CLI

`oagen resolve --spec <path> --format table|json` outputs the full resolution table for review. Use `--format json` for programmatic consumption.

## Versioning

The IR does not currently use a version constant. As a 0.x project with no external consumers yet, formal IR versioning is deferred until post-open-source when external emitters need a stable contract signal.

**Compile-time safety:** `assertNever` enforces exhaustive `switch` statements over `TypeRef.kind` at compile time. Adding a new variant causes build failures in any emitter that doesn't handle it — this is the primary compatibility mechanism.

**Walker/Mapper utilities:** `walkTypeRef` and `mapTypeRef` handle recursive traversal of `TypeRef` trees. Both visit `MapType.keyType` when present. The `mapTypeRef` mapper callback for `map` receives an optional third argument `mappedKey?: T` for the mapped key type.
